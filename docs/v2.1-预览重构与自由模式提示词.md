### 3.1 布局

**行数规则（写成一个纯函数，前后端都用同一套）**：

```js
// tileCount 返回实际渲染的格子数与 "还有" 数量。
// n <= 9  : 全显示，无 "还有" 格
// n >  9 : 显示 8 个 + 1 个 "还有 (n-8)" 格
function tileCount(n) {
  if (n <= 9) return { tiles: n, more: 0 };
  return { tiles: 8, more: n - 8 };
}
```

> **为什么是 8 而不是 9**：9 格全占满就没有位置放"还有 N"。用户明确要"8 个预览 + 还有 XXX"，所以 >9 时必然是 8 + 1。≤9 时全显示正好填满 3 行，也满足"不满 9 个显示所有子文件夹"。

**高度自适应**：容器不写 `height`，由行数决定。5 个格子 = 2 行 ≈ 2×(160+20)+8 = 368px；1 个格子 = 1 行 ≈ 188px，**不得留出 2 行空白**。

### 3.3 数据来源（一次请求出全部）

新增唯一入口：

```go
// BuildPanel 组装右栏两个区域。
// 一次调用完成：目录列举（一级）、封面选取、占用统计、缩略图查缓存。
// 全程不递归遍历整棵树，不做 PNG 解码（未命中走 pending）。
func (m *Manager) BuildPanel(side, mode, rel, focusAbs string) (Panel, error)
```

流程（严格按序）：

1. **定位焦点目录**：
   - 焦点是文件夹 → `dir = 它`，`highlight = 无`。
   - 焦点是卡片/zipmod → `dir = filepath.Dir(焦点)`，`highlight = 焦点绝对路径`。
   - 无焦点 → `dir = 当前列表目录`，`highlight = 无`。
2. **列一级目录**（`os.ReadDir` 一次，命中 `DirSnapshot` 缓存则零 IO）：
   - `subDirs` = 直接子文件夹（自然序）
   - `subFiles` = 直接子文件（自然序），按扩展名过滤：卡片模式只保留 `.png`；zipmod 模式无区域 B。
3. **区域 A（子文件夹）**：对每个子文件夹取**封面卡**（§3.4），`badge = "<recursiveFiles> 个文件"`。
4. **区域 B（卡片）**：直接子卡片，`badge = ""`（**不显示"N 个文件"**，用户明确要求）。
5. **缩略图**：按 `thumbKey` 查两级缓存，命中填 `thumb`，未命中 `pending=true` 并入队。
6. **排序**：自然序（`naturalLess`，见下）。不要用 `sort.Strings`——`22.7.9` 会排在 `22.7.10` 后面，用户看到会认为排序坏了。
7. **裁剪**：按 `tileCount(n)` 截断，`more = n - shown`。

```go
// naturalLess 按"人类阅读顺序"比较：数字段按数值比、其余按字节比、大小写不敏感。
func naturalLess(a, b string) bool
```

**返回结构**（前后端契约，字段名不许改）：

```go
type Tile struct {
    Kind     string `json:"kind"`     // folder | card | plugin | more | empty
    Name     string `json:"name"`
    Rel      string `json:"rel"`      // 相对类型根（POSIX）
    Abs      string `json:"abs"`      // 绝对路径（前端用于定位/打开）
    Badge    string `json:"badge"`    // "12 个文件" / "" （卡片格必须为空串）
    ThumbKey string `json:"thumbKey"` // 缓存键 = sha1(abs + "|" + size + "|" + mtime)
    Thumb    string `json:"thumb"`    // dataURI，未命中为空
    Pending  bool   `json:"pending"`
    Selected bool   `json:"selected"` // 焦点所在格
    RefCount int    `json:"refCount"` // 仅 zipmod 卡片格使用
}

type Section struct {
    ID      string `json:"id"`      // folders | cards | plugins
    Title   string `json:"title"`   // "子文件夹" / "此文件夹的卡片" / "引用此 GUID 的插件"
    Layout  string `json:"layout"`  // grid | list
    Total   int    `json:"total"`
    Tiles   []Tile `json:"tiles"`
    More    int    `json:"more"`    // 0 = 无"还有"格
    MoreLabel string `json:"moreLabel"` // "还有 14 个文件夹" / "还有 107 张角色卡"
    Visible bool   `json:"visible"` // false 时前端整块不渲染
    Empty   string `json:"empty"`   // 非空且 Visible=true 时显示的空态文案
}

type Panel struct {
    Focus    struct {
        Kind string `json:"kind"` // folder|card|mod|hidden|none
        Name string `json:"name"`
        Abs  string `json:"abs"`
        Info string `json:"info"` // 信息栏主文案
    } `json:"focus"`
    Sections []Section `json:"sections"` // 固定长度 2，顺序 A、B
    Gen      int64     `json:"gen"`      // 面板代数，前端用于丢弃过期响应
}
```

### 3.4 封面卡选取（性能陷阱，必须按此实现）

> **现状问题**：`app.go` 的 `findSampleCard()` 用 `filepath.Walk` 递归整棵子树找第一张 PNG。根目录 `female/` 下有 16150 个文件，每次切焦点都会全树遍历一次 —— 这是本轮最容易踩的性能坑。

```go
// pickCover 返回目录的"封面卡"绝对路径；找不到返回 ""。
//
// 规则（按序短路，绝不无限制递归）：
//  1. 直接子文件里自然序第一张 .png → 命中即返回（最常见，1 次 ReadDir）
//  2. 否则按子目录名自然序 BFS，深度 <= 3，最多访问 64 个目录
//  3. 仍无 → 返回 ""（前端渲染无封面占位，不是错误）
//
// 缓存：map[dir]coverEntry{path, dirMTime}。目录 mtime 未变则直接复用。
// 失效：事务提交时按"受影响目录 + 其所有祖先"批量清除。
func (m *Manager) pickCover(dir string) string
```

**必须避免的写法**：`Walk` 全树、每次焦点变化都重新找、用 `os.Stat` 判断每个候选人。

## 4. zipmod 预览（替换"无法预览"）

焦点为 zipmod 时，`BuildPanel` 走 zipmod 分支：

### 4.1 区域 A —— 使用该 zipmod 的卡片

- 数据源：`GlobalDepMap[guid]`（内存，O(k)）。
- 每个引用文件按类型分组统计：`角色卡(女) 12 · 场景卡 3 · 服装 1`，写在区域标题右侧作为副标题。

### 4.2 区域 B —— 引用该 GUID 的插件（DLL）

- 数据源：`PluginDepMap[guid]`（`[]string`，相对 `KKS_ROOT` 的路径）。
- **布局为 list（1 列行式，不是九宫格）**：DLL 无图，九宫格会显得空且文件名截断严重。
- 每行 h=44：`[SVG 插件图标] 文件名（14px，可 2 行）` + 次行灰色小字（相对目录，如 `BepInEx/plugins`）。
- 最多 8 行 + 1 行"还有 N 个插件"，同样遵守 `tileCount` 规则（>9 → 8+1；≤9 全显示）。
- 零引用 → `Visible=true, Empty="未被任何插件硬编码引用"`。
- 行点击 → 弹窗显示 DLL 完整路径 + 命中方式（UTF-8 / UTF-16LE）+ 该 DLL 命中的全部 GUID（来自 `PluginEntry.GUIDs`）。这是排查"为什么这个 mod 隔离不了"的关键信息。

### 4.3 信息栏

## 6. 自由模式功能补全

> **启用条件**：`opMode === 'free'`。安全模式下这些按钮/菜单项**不渲染**（不是禁用）。
> zipmod 模式下允许新建/重命名/删除（`mods` 侧）；`DEL-zipmod` 侧扁平结构，禁止"新建文件夹"。

### 6.1 新建文件夹（创建 + 立即重命名）

```
点击 [＋ 新建] 或 Ctrl+Shift+N
  → 后端 CmdMkdir(currentRel, defaultName)
  → 返回实际创建名（可能为 "新建文件夹 (2)"）
  → 列表刷新 + 新行进入编辑态（inline input，自动全选文件名）
  → 用户回车/失焦 → CmdRename(oldRel, newName)
  → 用户 Esc → 保留默认名 + toast "已创建「新建文件夹 (2)」"
```

**规则**：

- 默认名 `新建文件夹`；同名则 `新建文件夹 (2)`、`(3)`…（探测上限 99，超限报错）。
- 创建位置 = **当前列表路径**（不是焦点项内部）。若当前焦点是文件夹且用户从右键菜单进入，则创建在**该文件夹内**（菜单项文案改为"在此文件夹中新建"）。
- inline 编辑态：只允许一层，再次触发先提交上一个。
- 名称校验（前端即时 + 后端最终）：
  - 空 / 全空白 → 禁用确定
  - 含 `< > : " / \ | ? *` 或控制字符 → 红框 + 提示
  - 结尾为空格或 `.` → 拒绝（Windows 会静默改名）
  - 长度 > 100 字符 → 拒绝
  - 同目录已存在同名（不区分大小写）→ 提示"已存在同名项"
  - 保留名（`CON` `PRN` `AUX` `NUL` `COM1-9` `LPT1-9`）→ 拒绝
- 后端二次校验同上，返回结构化错误码（`NAME_INVALID` / `NAME_EXISTS` / `IO_ERROR`）。

### 6.2 重命名

- 入口：`F2`、右键"重命名"、单击已选中项的名称（第二次单击进入编辑，仿资源管理器）。
- 允许重命名：文件夹、卡片、zipmod（`mods` 侧与 `DEL-*` 侧均可）。
- 扩展名保护：若改名后扩展名变化（`.png` → `.txt`），弹确认：`修改扩展名会导致该文件不再被识别为角色卡，确定？`。zipmod 改扩展名直接拒绝。
- 事务：`rename` 步骤，可撤销。
- 被占用（Windows 下文件被游戏/看图软件打开）→ 失败并弹窗：`无法重命名：文件正在被其它程序使用`。
- 重命名后：更新索引 key（`Cards` / `Zipmods` 的 map key + `Rel`），`derive()`，清缩略图缓存（路径变了，但 `thumbKey` 含 path 会自动失效），清 `DirSnapshot`。

### 6.3 空白区域菜单

**触发**（三种都要实现）：

1. 列表空白处 **右键** → 打开目录菜单（主行为）。
2. 列表空白处 **左键单击** → 清除焦点 + 清除勾选（标准行为）。
3. 设置项 `blankLeftMenu`（默认 `false`）为 `true` 时，左键单击空白也打开菜单（满足"单击空白打开右键菜单"的字面需求，但默认不开启以免误触）。

> 判定"空白"：`e.target === container` 或 `!e.target.closest('.list-item')`。

**目录菜单内容**（自由模式）：

```
粘贴                    Ctrl+V     （剪贴板空 → 禁用并显示"剪贴板为空"）
────────────
新建文件夹               Ctrl+Shift+N
────────────
全选                    Ctrl+A
刷新                    F5
────────────
在资源管理器中打开
```

安全模式：仅 `全选 / 刷新 / 在资源管理器中打开`。
`invisible` / `回收站` 模式：仅 `全选 / 刷新`。

### 6.4 删除（进 `DELED`）

**目录约定**（新增，不污染现有结构）：

```
DELCARDS/
  DELED/
    female_card/     ← 对应 DEL-female_card 的同名种类
    male_card/
    scene/
    pose/
    coord_f/
    coord_m/
    zipmod/
    _trash.json      ← 回收站元数据（必须，见下）
```

`DELED/<spec>/<原相对路径>` 保留结构；zipmod 为扁平（原样文件名，重名加 `__2`）。

**为什么必须有 `_trash.json`**：zipmod 在 `mods` 下可能是嵌套路径（`mods/sub/a.zipmod`），删进 `DELED/zipmod/a.zipmod` 后就**丢失了原路径**，无法还原。元数据必须记录原绝对路径。

```go
type TrashMeta struct {
    OriginalAbs string `json:"originalAbs"` // 删除前的绝对路径
    Spec        string `json:"spec"`        // female_card / zipmod / ...
    TxID        string `json:"txId"`
    DeletedAt   int64  `json:"deletedAt"`
    Size        int64  `json:"size"`
    IsDir       bool   `json:"isDir"`
}
// file: DELCARDS/DELED/_trash.json  -> map[trashRel]TrashMeta
```

**语义与交互**：

- 删除 = `move` 到 `DELED/...`（同一磁盘，秒完成）。
- 二次确认弹窗：`将把 3 个项目移入回收站（共 12.4 MB），可在「回收站」中还原。`（危险色主按钮）。
- 删除文件夹 = **整棵子树一次移动**（不要逐个文件，否则 1000 个文件 = 1000 步 journal）。
- 删除后：`derive()`（若含 zipmod/卡片）、清快照与封面缓存、刷新两侧列表、写历史、toast。
- 回收站作为新的管理类型出现在下拉框：`回收站（DELED）`，只读浏览 + `[还原]` `[彻底删除]` 两个按钮。
  - 还原：按 `OriginalAbs` 移回；原父目录不存在则 `MkdirAll`；目标已存在 → 冲突弹窗（跳过 / 自动重命名）。
  - 彻底删除：输入条目名称确认 → `os.RemoveAll`（这是全项目**唯一**允许真删的地方）→ 清 `_trash.json` 条目。
- 安全模式下**没有**删除入口。

## 7. zipmod 管理：两个新按钮（逻辑由本节定义）

按钮位置：中列操作区，在"确认隔离/恢复启用"下方，仅 `mode === 'zipmod'` 时渲染。

```
[🩹 修复缺失 zipmod]     琥珀色
[🧹 隔离多余 zipmod]     中性色
```

两者都必须是**两阶段**：`Plan`（零副作用，出清单）→ 用户确认 → `Commit`（事务执行）。

### 7.1 修复缺失 zipmod

**"缺失"的严格定义**：

```go
missing := { g |
    ( g ∈ ⋃ Cards[*].GUIDs  ∨  g ∈ keys(PluginDepMap) )   // 被卡片或插件需要
    ∧ g ∉ GuidToZipmod                                     // 但 mods 里没有
    ∧ g ∉ IsolatedGuidMap                                  // 也不在隔离区（在隔离区属于"可修复"）
}
```

> 注意第二个条件：**插件需要但 mods 里没有** 也必须算缺失 —— 这种崩溃最难查。

**候选来源（按优先级）**：

1. `DEL-zipmod/*.zipmod`（被隔离的）
2. `DELED/zipmod/*.zipmod`（被删除进回收站的）

因此索引必须扩展：扫描时若 `DEL-zipmod` / `DELED/zipmod` 存在，解析其 manifest 并建表（带指纹缓存，**只在有缺失或进入 zipmod 模式时才扫**，避免无谓 IO）：

```go
// IndexData 扩展
IsolatedZipmods map[string]*ZipmodEntry `json:"isolatedZipmods"` // key: 绝对路径，Rel 存原相对路径
OriginRel       map[string]string       `json:"originRel"`       // GUID -> 在 mods 下的原相对路径
```

`OriginRel` 在**隔离时写入**（`isolate` 事务里记录 `srcRel`）；缺失时用它把文件放回原位，未知则放 `mods/` 根。

**计划结构**：

```go
type MissingFixPlan struct {
    PlanID        string `json:"planId"`
    Recoverable   []struct {
        GUID      string `json:"guid"`
        From      string `json:"from"`      // 隔离区/回收站中的绝对路径
        To        string `json:"to"`        // 目标绝对路径
        RefCards  int    `json:"refCards"`
        RefPlugins int   `json:"refPlugins"`
        Source    string `json:"source"`    // del-zipmod | deled
    } `json:"recoverable"`
    Unrecoverable []struct {
        GUID       string   `json:"guid"`
        RefCards   int      `json:"refCards"`
        RefPlugins int      `json:"refPlugins"`
        Sample     []string `json:"sample"` // 前 3 个引用文件
    } `json:"unrecoverable"`
    TotalBytes int64 `json:"totalBytes"`
}
```

**UI 展示**（模态框）：

```
可修复 3 个（共 84.2 MB）                        来源：隔离区 2 / 回收站 1
  ☑ com.example.mika_boots    被 14 卡 + 1 插件使用   隔离区 → mods/
  ☑ com.example.hair_v2       被 3 卡使用             隔离区 → mods/sub/
  ☐ ...

无法修复 2 个（本地不存在，需重新下载）
  com.example.missing_a       被 6 卡使用    引用示例：xxx.png, yyy.png
  ...
                                                            [取消] [开始修复]
```

**执行**：

1. 逐个走 `IsZipmodSafeToMoveEx(guid, {})` —— 修复是"移回"，依赖只会更全，理论上必过；仍要检查，防止目标已存在同名。
2. 目标已存在同 GUID 的 zipmod → 该项标记 `SKIPPED`（已存在，无需修复）。
3. 目标路径已存在同名文件但 GUID 不同 → 冲突，该项跳过并记录。
4. 单事务批量提交，失败整体回滚。
5. 提交后：更新索引（从 `IsolatedZipmods` 移除、加入 `Zipmods`）、`derive()`、清缓存、写历史、日志 `[fix-missing] 恢复 3 个 zipmod，跳过 1 个`。

**边界**：

- 未扫描完成（`!Scanned`）→ 直接返回 `BUSY`，不猜测。
- `missing == 0` → 按钮点击后直接 toast `没有缺失的 zipmod`，不弹空窗口。
- 修复后仍需刷新 `MissingGUIDs` 并返回新的缺失列表供 UI 显示"仍有 N 个未修复"。

### 7.2 隔离多余 zipmod

**"多余"的严格定义**（三个条件全部满足）：

```go
extra := { g |
    g ∈ GuidToZipmod
    ∧ len(GlobalDepMap[g]) == 0            // 无任何卡片引用
    ∧ len(PluginDepMap[g])  == 0           // 无任何 DLL 硬编码引用
    ∧ len(modDependents(g)) == 0           // 无其它 zipmod 依赖它
}
```

**永不自动隔离**（必须在计划里列出原因，让用户知道为什么没动它）：

| 情形 | 原因文案 |
|---|---|
| `GUID == ""`（manifest 解析失败） | `无法识别 GUID，需人工确认` |
| `CardEntry.ParseErr != ""` 影响到的引用 | 不适用（这是卡片侧） |
| 同一 GUID 有多个 zipmod 文件 | 保留字典序最小者作为主副本；其余标 `重复副本`（可选隔离） |
| 该 zipmod 自身依赖的 GUID 也缺失 | `依赖链不完整，隔离后更难恢复` |

**计划结构**：

```go
type ExtraPlan struct {
    PlanID     string `json:"planId"`
    Candidates []struct {
        GUID  string `json:"guid"`
        Path  string `json:"path"`
        Base  string `json:"base"`
        Size  int64  `json:"size"`
        Note  string `json:"note"` // "" | "重复副本"
    } `json:"candidates"`
    Skipped    []struct{ Path, Reason string } `json:"skipped"`
    TotalBytes int64 `json:"totalBytes"`
}
```

**UI**：默认**全选**候选，按大小降序；顶部显示 `将隔离 87 个 zipmod，释放 1.8 GB`；底部 `[取消] [隔离所选]`。

**执行**：

1. 每个候选**再跑一次** `IsZipmodSafeToMoveEx`（纵深防御：计划生成到用户点确认之间可能已启用某张卡）。
2. 目标 `DEL-zipmod/<base>`；重名 → `<name>__2.zipmod`，并记录 `OriginRel`。
3. 单事务；任一步失败 → 整体回滚并明确报错（不要"部分成功"这种模糊结果）。
4. 提交后 `derive()`、清缓存、写历史、日志 `[isolate-extra] 隔离 87 个，释放 1.8 GB，跳过 4 个（解析失败）`。

**为什么"多余"判定必须先 derive 再算**：若索引是脏的（上一次操作后未重建），会把在用的 mod 误判为多余 —— 这是最危险的单点。所以 `PlanIsolateExtra` 第一步固定调用 `derive()`。

## 8. 操作记录与回溯（`internal/tx` 落地）

### 8.1 目录

```
DELCARDS/_state/thumb/                  // 缩略图磁盘缓存（§9.3）
```

`txId` 格式：`20261113-180233-a3f2`（本地时间 + 4 位随机 hex），字典序即时间序。

### 8.2 事务 API（`internal/tx`）

```go
package tx

type Step struct {
    Kind  string `json:"kind"`  // move | copy | mkdir | rename | trash
    Src   string `json:"src"`
    Dst   string `json:"dst"`
    SrcFP FP     `json:"srcFp"` // 执行前的指纹（撤销校验用）
    DstFP FP     `json:"dstFp"` // 执行后的指纹
    State string `json:"state"` // intent | done | rolledback
    Err   string `json:"err,omitempty"`
}

type Tx struct {
    ID        string `json:"id"`
    Kind      string `json:"kind"`  // paste | isolate | delete | mkdir | rename | hide | fix-missing | isolate-extra
    Title     string `json:"title"` // 人类可读，用于历史列表
    StartedAt int64  `json:"startedAt"`
    Steps     []Step `json:"steps"`
    State     string `json:"state"` // open | committed | rolledback
    Logs      []string `json:"logs"`
}

func Begin(root, kind, title string) (*Tx, error)
func (t *Tx) Move(src, dst string) error   // 内部：先写 intent → 执行 → 标记 done
func (t *Tx) Copy(src, dst string) error
func (t *Tx) Mkdir(dir string) error
func (t *Tx) Rename(src, dst string) error
func (t *Tx) Commit() error                // 删除 journal 目录，写 history
func (t *Tx) Rollback() error              // 逆序回退，全部成功才标 rolledback
func LoadPending(root string) ([]*Tx, error) // 启动恢复
```

**硬性要求**：

- 每个 `Move/Copy/Mkdir/Rename` 调用**第一步**就把 `intent` 整体写盘（marshal 整个 Tx + `f.Sync()`）。步数上限 500，单次写入 < 200KB，可接受。
- `Commit` 前必须校验 `t.State == "open"`；重复 Commit/Commit 后 Rollback 直接报错（幂等保护）。
- 回滚规则：

| 步骤 | 回滚动作 |
|---|---|
| `move`（done） | `move(dst → src)`；src 已被占用 → 移到 `src.conflict-<txid>` 并记 error |
| `move`（intent，未 done） | `dst` 存在且 `src` 不存在 → 移回；`dst` 是半成品 → 删除 `dst` |
| `copy` | 删除本 tx 创建的 `dst`（目录则 `RemoveAll`，**仅限 trash/journal 之外的副本**） |
| `mkdir` | `os.Remove`（仅空目录；非空则保留 + warn，不阻断其它回滚） |
| `rename` | 改回原名 |
| `trash` | 从 `DELED/...` 移回 `OriginalAbs`，并删 `_trash.json` 条目 |

- **启动恢复**：`LoadPending` 扫 `_journal/*`，逐个 `Rollback`，结果写启动日志；UI 一条 warn：`检测到上次未完成的操作（粘贴 12 项），已自动还原。`
- 回滚失败 → 保留 journal，弹窗阻断：`自动还原失败：文件 X 被占用。请关闭相关程序后点击「重试还原」。`

### 8.3 历史与撤销

```go
type HistoryEntry struct {
    TxID      string `json:"txId"`
    Kind      string `json:"kind"`
    Title     string `json:"title"`
    At        int64  `json:"at"`
    Affected  int    `json:"affected"`
    Bytes     int64  `json:"bytes"`
    Status    string `json:"status"`  // committed | rolledback | reverted | partial
    Reverted  bool   `json:"reverted"`
    RevertErr string `json:"revertErr,omitempty"`
}
```

**撤销（回溯）语义**：

- 只允许撤销 `status == "committed"` 且 `reverted == false` 的条目。
- **前置校验（逐步骤）**：`Dst` 当前指纹必须与记录的 `DstFP` 一致。任一不符 → 拒绝整个撤销，弹窗指出第一个冲突文件：
  `无法撤销：A/b.png 已被外部修改。`
- 撤销 = 把该 tx 的 Steps 逆序执行（本质是同一个回滚器），成功后将原条目标 `reverted=true`，并**新增**一条 `kind=undo` 的历史（便于审计）。
- 撤销本身失败 → 部分回滚 + 保留 journal + 弹窗（不许静默）。
- 历史只保留 200 条，超出按时间淘汰；被淘汰的 tx 的 journal 已删除，因此**无法再撤销**（UI 上这些条目灰显 `超出可撤销范围`）。

### 8.4 历史窗口 UI

- 入口：顶栏右侧 `[🕘 操作记录]`（始终可见）。
- 面板 760×560：列表行 = `时间 · 操作名 · 影响 N 项 · 大小 · 状态`，右侧 `[撤销]`。
- 状态色：`已完成` 绿、`已回滚` 灰、`已撤销` 灰、`失败` 红。
- 顶部筛选：`全部 / 可撤销 / 已撤销`。
- 底部：`保留最近 200 条记录`。

## 9. 性能规范（"不重复扫盘"的具体落地）

### 9.1 本轮新增的三类缓存

| 缓存 | Key | 失效时机 | 容量 |
|---|---|---|---|
| `DirSnapshot` | 绝对目录路径 | 目录 mtime 变化 / 事务提交（受影响目录及其祖先） | LRU 128 |
| `coverCache` | 绝对目录路径 | 同上 | LRU 512 |
| `thumbLRU`（内存） | `thumbKey` | 永不主动失效（key 内已含 size+mtime） | 256 张 |

### 9.2 面板请求预算

单个 `BuildPanel` 必须满足：

- 磁盘操作 ≤ **2 次 `ReadDir`**（当前目录 + 至多 1 次封面兜底目录），且命中缓存时为 **0 次**。
- 解码 PNG **0 次**（全部走缓存；未命中只入队）。
- 耗时 P95 ≤ **30ms**（缓存命中）/ ≤ **80ms**（冷）。

### 9.3 缩略图队列（`internal/preview`）

```go
// Queue 是缩略图生成队列：有界并发、去重、优先级、批量通知。
type Queue struct {
    workers   int            // = 3（机械盘不要更高，SSD 也别超过 4）
    hi, lo    []string       // 高优先级（当前面板）/ 低优先级（预热）
    inflight  map[string]bool
    mem       *lruCache      // 256 张
    diskDir   string         // DELCARDS/_state/thumb
}

// Request 返回 (dataURI, pending)。
// 命中内存 → 立即返回；命中磁盘 → 读文件返回（不解码）；
// 都没有 → 入队并返回 ("", true)。
func (q *Queue) Request(abs string, fp Fingerprint, priority bool) (string, bool)
```

- 磁盘缓存路径：`thumb/<sha1(abs)[:2]>/<sha1(abs+size+mtime)>.jpg`，320×400、q82，约 20–50KB。
- 命中磁盘时**只读文件**，不重新解码。
- worker 完成后按 100ms 窗口批量发 `thumb:ready` 事件：`[{thumbKey, dataUri}]`，前端按 `thumbKey` 局部替换 `<img src>`（不重渲染整个面板）。
- 优先级：面板请求 `hi`；用户在某目录停留 > 300ms 时，把该目录后 24 张 `lo` 入队（预热）。
- **冷启动不生成缩略图**：16150 张 × 30ms = 8 分钟，绝不可接受。

### 9.4 禁止清单

- ❌ 在 `BuildPanel` 里 `filepath.Walk`。
- ❌ 在 `renderList` 里算统计。
- ❌ 为拿"占用数"去 `os.Stat` 每个引用文件。
- ❌ 每次焦点变化都重新 `newStatsAggregator`（现状 `GetFolderPreview` 就是这么干的，根目录会全树遍历）。
- ❌ 把 9 张 dataURI 每次都完整重发（前端按 `thumbKey` 复用，未变化的格子不换 `src`）。
