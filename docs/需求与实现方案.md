> **项目定位**：Koikatsu Sunshine (KKS) 资源及其 zipmod 依赖的安全管理桌面工具。

## 一、需求总览

需求分三轮提出，逐步演进。

### 1.1 第一轮：核心功能

**环境与前置**
- 克隆参考源码 `GenesisAN/KKCardModCheck`，阅读其 Go 源码（卡片解析、zipmod 依赖提取逻辑）
- **直接复用/移植**其底层 PNG 尾部数据读取、ZIP 内 `manifest.xml` GUID 解析，**严禁从零手写复杂二进制解析**
- 使用既有 `GUI.html` 作为 Wails 前端，替换其中 `mockInstalledDB` 等硬编码假数据

**路径与目录结构**

| 项目 | 路径 |
|---|---|
| 游戏根目录 | `KKS_ROOT`（如 `E:\KKV114`） |
| 隔离区根目录 | `DELCARDS_ROOT = KKS_ROOT/../DELCARDS` |
| 女卡 | `UserData/chara/female` |
| 男卡 | `UserData/chara/male` |
| 场景 | `UserData/Studio/scene` |
| POSE | `UserData/Studio/pose` |
| 女装 | `UserData/coordinate/female` |
| 男装 | `UserData/coordinate/male` |
| 工作室角色 | `UserData/Studio/character`（第二轮移除） |
| Zipmod | `mods` |

隔离区须自动创建 8 个子目录（只增不删）：
`DEL-female_card`、`DEL-male_card`、`DEL-scene`、`DEL-pose`、`DEL-coord_f`、`DEL-coord_m`、`DEL-studio_char`、`DEL-zipmod`

**核心逻辑约束**

1. **全局依赖图**：扫描全部类型文件提取 GUID，构建 `GlobalDepMap: map[string][]ReferrerFilePath`，记录每个 GUID 被哪些类型、哪些文件的绝对路径引用
2. **隔离保留结构**：移动 `female/subA/subB/card.png` 时，先在 DEL 区预建 `DEL-female_card/subA/subB/` 再移动；源目录变空**绝不删除**
3. **Zipmod 隔离**：移除被勾选卡片的引用后，若 GUID 仍被任何未勾选文件引用，**绝对不允许移动该 zipmod**；仅当彻底孤立才移动至 `DEL-zipmod/`（扁平化）
4. **恢复**：卡片移回原位（自动重建父目录）；zipmod 移回 `mods/`（同名则跳过）；DEL 区空目录可清理，游戏目录永不删除

**指定代码结构**

```go
type App struct {
    ctx context.Context
    manager *Manager
}

type Manager struct {
    KksRoot      string
    DelCardsRoot string
    ZipmodDB     map[string]string   // GUID -> zipmod绝对路径
    GlobalDepMap map[string][]string // GUID -> 引用该GUID的文件路径列表
}
```

**绑定方法**：`SelectKKSRoot`、`GetLeftTreeData`、`GetRightTreeData`、`ExecuteIsolate`、`ExecuteRestore`

### 1.2 第二轮：预览修复 + 状态区域 + 移除工作室角色

1. **PNG 预览无法显示** —— 场景卡/角色卡/服装卡等 PNG 卡无法预览，需修复
2. **状态区域** —— 位于「当前管理类型」之前：
   - 红底黑字 + 蓝色进度条
   - 选择路径前：进度条隐藏，文字「未选择路径」
   - 加载中：文字「正在加载」，背景红白闪烁（频率 1s）
   - 路径结构不符：红底黑字，文字「加载错误」，进度条中止变黄
   - 加载成功：进度条消失，文字「扫描完成：zipmod xxx 个，资源文件 xxx 个，依赖 GUID xxx 个，耗时 xxx ms」，背景变黑
3. **移除「工作室角色」** —— 不再扫描该路径，不创建对应 `DEL-XXX`，前端选项删除

### 1.3 第三轮：交互增强 + 自由修改模式 + 隐藏文件夹

1. **文件夹勾选级联** —— 勾选文件夹自动勾选其子文件夹和文件
2. **文件夹整体隔离/启用** —— 严格保留原本目录结构
3. **长名称处理** —— 末尾用 `...`，设置合理最大长度；鼠标点击让对应行显示完整内容（换行显示）
4. **焦点高亮** —— 当前预览文件所在行背景改为浅蓝色
5. **焦点语义变更** —— 鼠标点击某行**不会自动勾选**，只是切换焦点、切换预览图片
6. **文件夹预览** —— 焦点位于文件夹时不显示图片，显示第一级子文件夹数量与卡片数量；右侧用最多 3 个窗格预览子文件夹，多的在后面放一个显示「还有 xxx」（换行显示文件夹名）的窗格，组成 2×2
7. **模式切换按钮** —— 窗口上方选择 KKS 路径的蓝色按钮右侧，红/绿切换按钮
8. **自由修改模式** —— 两列上方新增复制/剪切/粘贴按钮（类似 Windows 资源管理器）；右键菜单含复制/剪切/粘贴
9. **安全加载隔离模式** —— 右键菜单：启用（右侧栏）、隔离（左侧栏）
10. **复制/剪切/粘贴逻辑**
    - zipmod：等于启用/隔离，取决于从哪复制/粘贴/剪切到哪，**必须严格遵守无 zipmod 缺失原则**
    - PNG：目标路径存在同名 PNG 则取消复制操作，弹出错误「无法复制」；可跳出「保留路径相同」前提，忽略路径相同，任意操作
11. **隐藏空文件夹** —— KKS 主目录或 DEL-XXX 路径下某个文件夹空了时，文件夹最右侧出现隐藏按钮（眼睛加斜杠图标）
    - 隐藏不是直接删除；程序运行时在 DELCARDS 路径下创建 `/DEL-invisible/` 文件夹，存放 `KKSinvisible.json`、`DELinvisible.json`（被隐藏文件夹路径信息）、`OriginKKS.json`、`OriginDEL.json`（原本路径的完整目录树，只记录文件夹）
    - 隐藏后删除源空文件夹；若内部有文件则提示「无法删除，不是空文件，存在 XXX 文件」
12. **路径重建** —— 文件/文件夹启用/隔离时父文件夹已被删除，依据 invisible JSON 重建路径后再操作
13. **新增管理种类「隐藏的文件夹」** —— 该模式下启用/隔离按钮变灰禁用；新增恢复按钮，选择/多选文件夹后通过恢复按钮恢复（其它种类不显示该按钮）

## 三、模块一：解析层（parser.go）

### 3.1 manifest.xml GUID 解析

移植自 `KKCardModCheck/util/ModXml.go`，并强化了健壮性。

```go
type ModManifest struct {
    GUID, Version, Name, Author, Description, Website, Game, MD5, FileName string
}

func ReadModManifest(src string) (ModManifest, error)
```

**处理流程**：

1. `os.Stat` 检查文件存在且非空
2. `zip.OpenReader` 打开（zipmod 本质是 zip）
3. 遍历条目查找 `manifest.xml`（按 `FileInfo().Name()` 匹配，支持子目录）
4. 读取内容 → **UTF-16 检测与转换** → `xml.Unmarshal`
5. 解析失败 → **移除多余闭合标签**修补 → 二次解析
6. 未找到 `manifest.xml` → **兜底**：遍历所有 `.xml` 条目，取第一个能解析出 GUID 的

**UTF-16 处理**：

```go
func isLikelyUTF16(data []byte) bool {
    return len(data) >= 2 && (data[0] == 0xFF && data[1] == 0xFE || data[0] == 0xFE && data[1] == 0xFF)
}
// BOM 检测 → utf16.Decode → UTF-8
```

**畸形 XML 修补**（移植 `removeUnmatchedClosingTags`）：

维护标签栈，扫描所有 `<...>` 片段：
- 注释 / DOCTYPE / 处理指令 → 原样保留
- 自闭合标签 `<tag/>` → 保留，不入栈
- 开标签 → 压栈
- 闭合标签 → 与栈顶匹配则弹栈并保留；不匹配则**删除**（这是多余的闭合标签）

> **对参考实现的增强**：原实现只删除多余闭合标签。若原文件**缺少**闭合标签（栈非空），修补后仍不是合法 XML。本实现在末尾按栈的逆序补齐剩余闭合标签，保证修补结果一定能被 `xml.Unmarshal` 解析。

### 3.2 卡片依赖 GUID 提取

```go
func ParseCardGUIDs(path string) ([]string, error)
func ParseCardGUIDsFromBytes(data []byte, path string) ([]string, error)
```

**双通道设计**：

**通道 A —— illusionsCard 正规解析**（优先）

```
util.PngBytesRead(data)          // 定位 PNG IEND 之后的追加数据、识别卡片类型
  → ic.ReadCard(pgb)             // 工厂按类型分派 reader
  → card.GetZipmodsDependencies()  // 汇总 ExtendedList[*].RequiredZipmodGUIDs
  → 若为 *KK.KKSceneCard，追加 sceneItemZipmodDependencies(scene)
```

场景卡的 `sceneItemZipmodDependencies` 从 `SceneExtended[UARExtID].Data["itemInfo"]` 取每个 `[]byte`，用 `Base.ResolveInfo.UnmarshalMsg` 解出 GUID —— 这是场景卡特有的依赖来源，角色卡没有。

**通道 B —— 兜底扫描**（保证任何卡型都能提取）

在 PNG 的 IEND 之后的数据中查找 `ModID` 键的原始字节（msgpack 中 ResolveInfo 映射的第一个键），向前回溯 1~5 字节寻找可能的 msgpack map 头（`0x80-0x8f` fixmap / `0xde` map16 / `0xdf` map32），用 `Base.ResolveInfo.UnmarshalMsg` 解码并取 `GUID` 字段。

```go
var modIDMarker = []byte("ModID")
```

**为什么需要通道 B**：`illusionsCard` 的 `cardReaderMap` 只登记了 `CT_KK`、`CT_KKCSP`、`CT_KKS`、`CT_KKC`、`CT_KKSC` 五种卡型。KKS 的 POSE 卡、服装卡等若使用未登记的容器格式，通道 A 会失败；通道 B 直接扫 msgpack 负载，与容器格式无关。

**两个通道的结果取并集去重**，最终按字典序排序输出。

## 四、模块二：核心管理器（manager.go）

### 4.1 Manager 状态

```go
type Manager struct {
    mu sync.RWMutex

    KksRoot      string            // 游戏根目录（绝对路径）
    DelCardsRoot string            // 隔离区根 = KKS_ROOT/../DELCARDS

    ZipmodDB     map[string]string // GUID -> zipmod 绝对路径
    GlobalDepMap map[string][]string // GUID -> 引用该 GUID 的文件绝对路径列表
    FileDeps     map[string][]string // 资源文件路径 -> 其依赖 GUID 列表
    DelFileDeps  map[string][]string // 隔离区文件路径 -> 其依赖 GUID 列表
    ModDeps      map[string][]string // zipmod 路径 -> 其声明依赖的 GUID 列表

    Scanned    bool
    clipboard  *Clipboard
    invisible  *InvisibleStore
}
```

**锁策略**：

| 方法 | 锁 | 说明 |
|---|---|---|
| `ScanAll` | 写锁 | 全量重建索引 |
| `Isolate` / `Restore` | 写锁 | 修改文件与索引 |
| `Paste` | 写锁 | 修改文件与索引 |
| `buildTree` | 写锁 | 内部 `depsFor` 会回写 `DelFileDeps` 缓存 |
| `buildModsTree` | 写锁 | 同上 |
| `GetGlobalDepInfo` | 读锁 | 只读统计 |

> 早期版本 `buildTree` 使用读锁，但 `depsFor` 会写入 `DelFileDeps` → **数据竞争**。已改为写锁，并用 `concurrency_test.go` + `go test -race` 固化。

### 4.3 隔离区目录创建

```go
func (m *Manager) EnsureDelDirs() error
```

创建 `DELCARDS_ROOT` 及其全部子目录。**实际创建 7 个**：6 个资源类型（`DEL-female_card`、`DEL-male_card`、`DEL-scene`、`DEL-pose`、`DEL-coord_f`、`DEL-coord_m`）+ `DEL-zipmod`。

### 4.4 目录结构校验

```go
var RequiredDirs = []string{

    "UserData/Studio/pose",
    "UserData/coordinate/female",

func (m *Manager) ValidateRoot() (missing []string, err error)
```

**必需 vs 可选的区分（重要决策）**：

真实 KKS 安装中 **`UserData/coordinate/male` 常常不存在**（很多安装没有男装资源库）。若把全部资源目录都列为必需，程序会直接报「加载错误」而完全不可用。

因此：
- `RequiredDirs`（缺失即报错）：chara/female、chara/male、Studio/scene、Studio/pose、coordinate/female、mods
- 可选目录（如 coordinate/male）：缺失只导致该类型列表为空，不阻断程序

### 4.5 全量扫描

```go
func (m *Manager) ScanAll(progress func(phase string, done, total int)) ScanResult
```

**两阶段 + 进度回调**：

```
阶段一（phase="zipmod"）：
    遍历 mods/ 下所有 .zipmod
    → ReadModManifest 取 GUID → ZipmodDB[guid] = path
    → 同一 GUID 出现多次时保留第一个（避免误移动）
    → ReadModManifestDependencies 提取 mod 间依赖 → ModDeps
    → 进度回调 (done, len(modFiles))

阶段二（phase="resource"）：
    先收集 6 类资源目录的全部文件，统计总数（便于进度条按整体推进）
    → 逐个 ParseCardGUIDs
    → FileDeps[path] = guids
    → GlobalDepMap[guid] = append(..., path)
    → 进度回调 (done, totalResources)

阶段三：
    统计本地缺失的 mod（GlobalDepMap 中有但 ZipmodDB 中无）
```

`ScanResult` 结构：

```go
type ScanResult struct {
    ZipmodCount, ResourceCount, DepGUIDCount, FailedFiles, FailedZipmods int
    MissingMods   []string
    ScanDurationMS int64
}
```

**容错策略**：单个文件解析失败只计入 `FailedFiles`，不影响整体扫描（扫描面对上万文件，必须容忍个别坏文件）。

> 与之相对，**移动操作**使用 `collectFilesStrict`（遇到读取错误即返回错误），因为移动场景下任何读取失败都可能导致结构丢失。

### 4.6 隔离逻辑（核心）

```go
func (m *Manager) Isolate(cardPaths []string) IsolateResult
```

**流程**：

```
前置校验：cardPaths 非空；m.Scanned 为 true（未扫描则拒绝，避免在不完整依赖图上操作）

步骤 1 —— 规划：
  对每个待隔离条目：
    classifyResource(src) → 判定所属类型 + 相对目录
    若为文件：直接生成 movePlan
    若为文件夹：collectFilesStrict 展开为文件列表，
                每个文件按 classifyResource 得到各自的相对目录
                （这样目录结构天然保留，依赖图逻辑可完全复用）
    空文件夹：单独创建目标空目录并记录日志

步骤 2 —— 收集 GUID：
  遍历 plans，汇总所有被勾选文件依赖的 GUID → selectedGUIDs

步骤 3 —— 移动资源文件：
  对每个 plan：
    ensureTargetParent(dst)      // 父目录若被隐藏删除则重建
    目标已存在 → 跳过并记错误（绝不覆盖）
    moveFile(src, dst)
    记录 DelFileDeps[dst] = FileDeps[src]
    removeDep(src)               // 从全局依赖图移除该文件的所有引用

步骤 4 —— 判定可移动的 zipmod：
  对每个 guid in selectedGUIDs：
    modPath = ZipmodDB[guid]；本地没有 → 跳过
    remaining = GlobalDepMap[guid] 中排除本次 selectedSet 的部分
    若 remaining 非空 → 【保留 MOD】记警告日志，列出仍被谁引用
    若存在其它 zipmod 依赖它（ModDeps 反查） → 【保留 MOD】
    否则 → 移动到 DEL-zipmod/（扁平化），从 ZipmodDB 删除
```

**核心不变式**：

```
移动 zipmod 的充要条件 = 该 GUID 在移除被勾选文件引用后，
                          且扣除 mod 间依赖后，无任何存活文件引用它
```

`removeDep` 需要同时清理 `FileDeps` 与 `GlobalDepMap` 中所有指向该路径的条目，并删除空的 GUID 条目。

### 4.7 恢复逻辑

```go
func (m *Manager) Restore(cardPaths []string) RestoreResult
```

```
对每个条目：
  若在 DEL-zipmod 下 → restoreZipmod（移回 mods/，同名则跳过）
  否则 classifyDelResource → 类型 + 相对目录
    若为文件夹 → collectFilesStrict 展开，逐个 restoreSingleFile
                  空文件夹 → 只重建目录
    若为文件   → restoreSingleFile

restoreSingleFile:
  dst = SourceDir(kind) + relDir + basename
  ensureTargetParent(dst)        // 父目录若被隐藏删除则重建
  目标已存在 → 跳过并记错误（绝不覆盖）
  moveFile(abs, dst)
  依赖关系写回：FileDeps[dst] = DelFileDeps[abs]，
                GlobalDepMap[guid] = append(..., dst)

最后：cleanEmptyDirs(DelCardsRoot)  仅清理隔离区空目录
```

### 4.8 文件移动与复制

```go
func moveFile(src, dst string) error   // 移动
func copyPath(src, dst string) error   // 复制（支持整个目录树）
func copyFile(src, dst string, perm os.FileMode) error
```

**moveFile 策略**：
1. 先 `os.Rename`（同盘高效）
2. 失败则降级为「复制 → fsync → 校验大小 → 删除源」（跨设备）
3. **绝不覆盖已存在的目标**（`O_EXCL` + 预检查）
4. 复制后大小不一致则**保留源文件**并报错

**copyPath 策略**：文件 → `copyFile`；目录 → 递归创建并逐项复制。目标已存在直接报错。

### 4.9 空目录清理

```go
func (m *Manager) cleanEmptyDirs(root string) int
```

自底向上（按路径长度降序）删除空目录。

**保护名单**（这些目录永不删除）：
- 7 个标准隔离子目录（`DEL-female_card` 等 + `DEL-zipmod`）
- `DEL-invisible`（内含 JSON 状态文件）

> 早期版本未保护标准子目录，导致恢复操作后 `DEL-zipmod` 等目录被整个删掉。已修复并用测试固化。

## 五、模块三：缩略图预览（preview.go）

### 5.1 问题根因

初版前端使用 `<img src="file:///E:/KKV114/...">`，Wails v2 的 WebView 出于安全策略拦截本地绝对路径 → `<img>` 的 `onerror` 触发 → 只显示文件名文本。

**不是格式解析失败，而是路径加载方式不被允许。**

### 5.2 解决方案

后端读图 → 缩放 → 编码 → base64 data URI 返回，前端 `<img src="data:image/jpeg;base64,...">`。

```go
const (
    previewMaxWidth   = 320
    previewMaxHeight  = 400
    previewMinPixels  = 32
    previewMaxPixels  = 80_000_000
    previewMaxFileSize = 256 << 20   // 256MB
    previewJPEGQuality = 82
)

type PreviewData struct {
    DataURI      string `json:"dataUri"`
    Width, Height int
    SourceWidth, SourceHeight int
    Message      string `json:"message"`
}

func (m *Manager) BuildPreview(path string) (PreviewData, error)
```

### 5.3 处理流程

```
1. 路径白名单校验
   pathAllowed(abs): 必须位于 KKS_ROOT 或 DELCARDS_ROOT 内
   （避免前端传入任意路径读取系统文件）

2. 文件检查：存在、非目录、非空、≤256MB

3. 解码：
   a) image.DecodeConfig(f) → 若 format=="png" 且像素数 ≤80M：
        f.Seek(0) → png.Decode(f)
        若尺寸 ≥32×32 → 直接采用
   b) 否则回退：findLargestPNGFrame(path)
        读全文件 → 遍历所有 PNG 签名 (89 50 4E 47 0D 0A 1A 0A)
        → png.Decode 每一帧 → 取面积最大的一张

4. flattenOnWhite(img)
   卡片 PNG 常带透明背景，JPEG 不支持透明 →
   先画到白底（image/draw.Src + draw.Over）

5. scaleToFit(img, 320, 400)
   等比缩放；已小于限制则原样返回
   使用 golang.org/x/image/draw.CatmullRom（高质量）

6. jpeg.Encode(buf, scaled, &jpeg.Options{Quality: 82})

7. "data:image/jpeg;base64," + base64.StdEncoding.EncodeToString(buf)
```

### 5.4 KKS 卡片结构兼容性

KKS 卡片文件结构为 `[完整 PNG 图片][IEND 之后的追加数据]`。Go 的 PNG 解码器读到 IEND 即停止，**尾随数据被自动忽略**，因此 `png.Decode` 可直接工作。

已用测试固化（`cardimage_test.go`）：构造「PNG + 4096 字节追加数据」的卡片文件，验证能正确解析出图片。

### 5.5 为什么必须缩放

用户实测环境中的卡片有 **42MB、7.5MB、2.7MB** 等规格。直接 base64 传输会导致 WebView 卡死。缩放后单张缩略图约 20~60 KB。

## 六、模块四：隐藏文件夹（invisible.go）

### 6.1 状态文件布局

程序运行时在 `DELCARDS_ROOT/DEL-invisible/` 下创建：

| 文件 | 内容 | 结构 |
|---|---|---|
| `KKSinvisible.json` | 被隐藏的 KKS 侧文件夹 | `{"kksFolders": ["UserData/chara/female/xxx", ...]}` |
| `DELinvisible.json` | 被隐藏的 DEL 侧文件夹 | `{"delFolders": ["DEL-female_card/xxx", ...]}` |
| `OriginKKS.json` | KKS 侧原始目录树 | `{"UserData/chara/female/xxx": ["sub1", "sub1/sub2", ...]}` |
| `OriginDEL.json` | DEL 侧原始目录树 | 同上，键为相对 DELCARDS_ROOT 的路径 |

**路径表示**：KKS 侧相对 `KKS_ROOT`，DEL 侧相对 `DELCARDS_ROOT`，统一用 POSIX 分隔符。

**目录树只记录文件夹，不记录文件** —— 文件的位置由 `DEL-XXX` 的目录结构自然体现。

**四个文件在程序启动时即创建**（`ensureStateFiles`），而非首次隐藏时才生成。

**原子写入**：先写 `.tmp` 再 `os.Rename` 替换，避免中途崩溃导致状态文件损坏。

### 6.2 隐藏流程

```go
func (s *InvisibleStore) HideFolders(paths []string, side string) HideResult
```

```
对每个路径：
  1. 判定归属侧（classify）：在 KKS_ROOT 内 → kks；在 DELCARDS_ROOT 内 → del
  2. 必须是文件夹
  3. 校验为空：countFilesIn(root) 递归统计文件数
     若 > 0 → 跳过，日志「无法删除，不是空文件，存在 N 个文件：<路径>」
  4. captureFolderTree(root)：记录全部子目录的相对路径
  5. 写入状态：
       kks → OriginKKS[rel] = tree; KKSinvisible += rel
       del → OriginDEL[rel] = tree; DELinvisible += rel
  6. os.RemoveAll(root) 删除源空文件夹
     删除失败 → 回滚状态记录（从 map 删除、从列表移除）
  7. 持久化四个 JSON 文件
```

### 6.3 恢复流程

```go
func (s *InvisibleStore) RestoreFolders(paths []string) InvisibleRestoreResult
```

```
对每个相对路径：
  在 KKSinvisible 中找到 → recreateFolderTree(abs, OriginKKS[rel])
                          从列表移除、删除 Origin 条目
  在 DELinvisible 中找到 → 同理
  都找不到 → 记「未找到隐藏记录」错误
```

`recreateFolderTree(root, tree)`：创建 root，再按 tree 中的相对路径逐个 `MkdirAll`。

### 6.4 路径重建（自动）

```go
func (s *InvisibleStore) EnsurePathForOperation(absTarget string) (bool, error)
```

**触发时机**：隔离/恢复操作移动文件前，若目标文件的父目录不存在。

```
1. 父目录存在 → 直接返回（无需重建）
2. 读取隐藏记录，找出能作为 target 祖先的最深层隐藏条目
   （在 KKS 侧与 DEL 侧分别查找，取路径最长者）
3. 找到 → recreateFolderTree 重建该隐藏条目 → 再 MkdirAll 确保更深层级
   返回 true（表示发生了重建）
4. 未找到 → 直接 MkdirAll 父目录
```

`Manager.ensureTargetParent(targetFile)` 是其封装，在 `Isolate` 与 `Restore` 中统一调用。

### 6.5 隐藏文件夹管理界面

新增管理种类 `mode = "invisible"`：

```go
func (a *App) GetInvisibleTreeData() string
```

返回左右两侧数据：
- 左侧：被隐藏的 KKS 侧文件夹（`ID` = 绝对路径，`Name` = 相对路径）
- 右侧：被隐藏的 DEL 侧文件夹

该模式下：
- 「确认隔离」「恢复启用」按钮**变灰禁用**
- 显示「恢复隐藏文件夹」按钮（其它种类不显示）

## 七、模块五：剪贴板（clipboard.go）

### 7.1 状态

```go

    ClipboardNone = ""
    ClipboardCopy = "copy"
    ClipboardCut  = "cut"
)

const (
    SideKKS = "kks"  // 游戏主目录侧
    SideDEL = "del"  // 隔离区侧
)

type ClipboardState struct {
    Op         string   `json:"op"`
    Paths      []string `json:"paths"`
    SourceSide string   `json:"sourceSide"`
    Mode       string   `json:"mode"`
}

type Clipboard struct {
    mu    sync.RWMutex
    state ClipboardState
}
```

### 7.2 粘贴流程

```go
func (m *Manager) Paste(targetDir, targetSide, targetMode string) ClipboardResult
```

**预检阶段（全部通过才执行）**：

```
对每个源：
  1. 规范化路径、检查存在性
  2. isZipmod = 扩展名 == ".zipmod"    ← 以扩展名判定，而非 GUID 是否解析成功
  3. 目标冲突检查：os.Stat(dst) 存在 → 记录 conflict，break
     （冲突时整个操作取消，报「无法复制：目标已存在同名文件 X」）
  4. zipmod 安全校验（仅当 sourceSide==kks 且 targetSide==del，即「移出 mods」）：
     a. GUID 为空 → 保守拒绝：
        「无法隔离：X 无法识别 GUID，无法确认依赖关系，已保留原文件。」
     b. zipmodStillReferenced(guid, src) 非空 → 拒绝：
        「无法隔离：X (GUID Y) 仍被 N 个资源引用，例如: ...」
```

**执行阶段**：

```
对每个 plan：
  effectiveOp = isZipmod ? ClipboardCut : state.Op
  剪切/移动 → moveFile + afterResourceMoved（更新依赖图）
  复制     → copyPath（源保留）

若 state.Op == ClipboardCut → 剪切完成后清空剪贴板（与资源管理器一致）
```

### 7.3 两条硬性规则

**规则一 —— zipmod 的复制语义等同移动**

需求原文：「对于 zipmod 的处理逻辑（等于启用，隔离，取决于从哪里复制/粘贴/剪切到哪里）」。

若 zipmod 的「复制」保留源文件，则「复制到隔离区」等于**没隔离** —— mod 还在 `mods` 里，隔离区多一份副本。因此 zipmod 一律执行移动：

| 源 → 目标 | 语义 | 效果 |
|---|---|---|
| mods → DEL-zipmod | 隔离 | 从 mods 移走 |
| DEL-zipmod → mods | 启用 | 移回 mods |

**规则二 —— PNG 忽略路径相同，任意操作**

需求原文：「可以直接跳出原本『保留路径相同』的前提，忽略路径相同，任意操作 png 文件，类似文件资源管理器」。

实现：PNG 不做「同侧禁止」的限制，只有**目标存在同名文件**时才拒绝。

**同名冲突的整体取消**：预检阶段一旦发现冲突即 `break`，不执行任何复制，并报「无法复制」。

### 7.4 依赖图维护

```go
func (m *Manager) afterResourceMoved(src, dst string, isZipmod bool, guid string)
```

- zipmod：更新 `ZipmodDB[guid] = dst` 或删除条目；`removeDep(src)`
- 资源文件：重新解析 dst 的依赖 → `FileDeps[dst]`，追加到 `GlobalDepMap`；`removeDep(src)`

### 7.5 zipmod 依赖检查

```go
func (m *Manager) zipmodStillReferenced(guid, excludePath string) []string
```

遍历 `GlobalDepMap[guid]`，排除 `excludePath`（正在移动的 zipmod 自身），且只统计**真实存在**的文件（已隔离的文件不在此列表中，但需防御性检查）。

### 9.3 文件夹勾选级联

```javascript
function collectDescendants(nodes, item) {
    const ids = [item.id];
    const prefix = item.path ? `${item.path}/${item.name}` : item.name;
    nodes.forEach(n => {
        if (n.path === prefix || n.path.startsWith(prefix + '/')) {
            ids.push(n.id);
        }
    });
    return ids;
}
```

利用 `path` 字段的前缀匹配：若文件夹的 `path` 为 `A`、名为 `B`，其子孙的 `path` 必为 `A/B` 或以 `A/B/` 开头。

```javascript
function setItemSelected(side, item, checked) {
    const targets = item.type === 'folder'
        ? collectDescendants(nodes, item)
        : [item.id];
    targets.forEach(id => checked ? selectedSet.add(id) : selectedSet.delete(id));
}
```

文件夹的勾选状态由 `isItemSelected` 计算：全部子孙都被勾选才算勾上。

「全选」复选框也改为包含当前目录下的文件夹（因而级联勾选整棵子树）。

## 十一、关键安全决策汇总

| # | 决策 | 理由 |
|---|---|---|
| 1 | zipmod 的「复制」语义等同移动 | 否则「复制到隔离区」等于没隔离，mod 仍留在 `mods` |
| 2 | zipmod 以**扩展名**判定，而非 GUID 是否解析成功 | 否则 manifest 损坏的 zipmod 会绕过依赖检查被移走，造成依赖缺失 |
| 3 | GUID 解析失败时**保守拒绝**移出 | 无法确认依赖归属时，宁可不动 |
| 4 | 依赖检查只看**真实存在**的文件 | 已隔离的文件不应阻止 mod 移走 |
| 5 | 移动/复制**绝不覆盖**已存在的目标 | 避免破坏用户数据 |
| 6 | 同名冲突**整体取消**整个操作 | 符合需求「取消复制操作」 |
| 7 | 未完成全局扫描时**拒绝**隔离 | 避免在不完整依赖图上误删 mod |
| 8 | 必需目录与可选目录**分离** | 真实安装常缺 `coordinate/male`，若列为必需则程序完全不可用 |
| 9 | 7 个标准隔离子目录 + `DEL-invisible` **受保护** | 不被空目录清理误删 |
| 10 | 隐藏文件夹保存**目录树**而非单个文件夹 | 恢复时能还原整棵子树 |
| 11 | 隐藏状态**原子写入**（tmp + rename） | 避免中途崩溃损坏状态 |
| 12 | 缩略图**必须缩放** | 用户的卡片达 42MB，直接 base64 会卡死 WebView |
| 13 | 预览路径**白名单**校验 | 避免前端传入任意路径读取系统文件 |
| 14 | 扫描容忍坏文件，移动不容忍 | 扫描面对上万文件；移动失败会导致结构丢失 |
| 15 | 复制粘贴**不做路径同侧限制**（PNG） | 需求明确要求「忽略路径相同，任意操作」 |
| 16 | 隐藏操作前校验递归文件数为 0 | 需求要求「隐藏空文件夹」 |

## 十三、已知限制与后续建议

### 13.1 当前限制

1. **自由修改模式对 PNG 不做依赖保护** —— 这是「自由修改」的本意。zipmod 仍受保护（会被拦截有依赖的项），但 PNG 完全自由。请用户自行留意。

2. **「粘贴到此处」的目标目录推断** —— 焦点不在文件夹上时，靠当前目录反推。在空目录中可能不准确（会提示「请先双击进入一个文件夹」）。

3. **隐藏功能只处理空文件夹** —— 非空文件夹点击隐藏按钮会提示「无法删除，不是空文件，存在 N 个文件」，符合需求。

4. **`DEL-studio_char` 遗留目录** —— 旧版本创建的空目录，新版不再维护。`cleanEmptyDirs` 会在下次恢复操作时自动清理（因为它已不在保护名单中）。

5. **未在真实 KKS 上执行过隔离/恢复** —— 所有破坏性操作的验证都在临时目录中完成。建议用户首次使用前先拿不重要的卡片试跑。

### 13.2 后续建议

1. **依赖图增量更新** —— 当前每次改动全量重扫，可改为按文件 mtime 增量维护。
2. **剪贴板跨会话持久化** —— 当前剪贴板仅存于内存，程序重启即丢失。
3. **隐藏文件的记录** —— 当前目录树不记录文件，若将来支持隐藏非空文件夹需扩展数据结构。
4. **操作撤销** —— 隔离/恢复已记录完整日志，可基于此实现撤销栈。

## 十四、开发过程中修复的缺陷

测试驱动开发过程中发现并修复的**真实缺陷**，均已用测试固化。

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | `cleanEmptyDirs` 会删掉标准隔离子目录**本身** | 违反「只增不删」要求 | 加保护名单 |
| 2 | `buildTree` / `depsFor` 与后台扫描协程**数据竞争** | 运行时可能 map 并发读写崩溃 | 改用写锁 + `-race` 测试 |
| 3 | 参考实现的 XML 修补遇**缺闭合标签**时结果仍不合法 | manifest 解析失败 | 末尾按栈逆序补齐闭合标签 |
| 4 | 前端用 `file:///` 加载图片被 WebView 拦截 | **所有 PNG 预览失败** | 改为后端返回 base64 data URI |
| 5 | 缩略图未缩放，42MB 卡片直接 base64 | WebView 卡死 | 缩放到 320×400 + JPEG q82 |
| 6 | 「重新扫描」按钮**根本没触发重扫** | 依赖图不更新 | 新增 `Rescan()` 绑定 |
| 7 | `ScanAll` 进度只覆盖 zipmod 阶段 | 进度条反映失真 | 改为两阶段进度回调 |
| 8 | zipmod 按 GUID 判定，**解析失败会绕过依赖检查** | **可能造成依赖缺失** | 改按扩展名判定 + GUID 失败保守拒绝 |
| 9 | zipmod 的「复制」保留源文件 | 「复制到隔离区」等于没隔离 | zipmod 一律执行移动 |
| 10 | 隐藏状态文件未在启动时创建 | 用户查看时目录为空 | `ensureStateFiles()` 启动即创建 |
| 11 | `go vet` 报 JSON 标签重复 | 状态文件结构混乱 | 字段名改为 `kksFolders` / `delFolders` |
