## 0. 你的角色与任务

你是一名资深 Go / Wails 桌面应用工程师，接手一个**已经能跑、但架构和交互都有硬伤**的项目：`KKSCARDS管理工具`（KKS = Koikatsu Sunshine 游戏资源管理器）。

现状：Go 1.27.4 + Wails v2.17.1 + 单文件 `frontend/index.html`（1300 行内联 JS），生产代码约 5100 行，测试 59 个用例。

## 3. 必须修复的缺陷（附根因与精确修法）

这一节列的每一条都能用"打开文件、看这几行"验证。**先修完这一节，再谈架构。**

### 3.1 【致命】左键单击任何条目无反应

**现象**：点文件、点文件夹，焦点不变，高亮不出现，预览不刷新。

**根因**：`frontend/index.html:734` 的 `const hideBtn` 声明在 `if (item.type === 'folder') { ... }` 块**内部**，而 `frontend/index.html:751-756` 的 `div.onclick` 在块**外部**引用了它。`const` 是块级作用域，块外不可见 → 每次点击都抛 `ReferenceError: hideBtn is not defined` → 后面的 `setFocus(side, item)` 永远执行不到。

```js
// 现状（错）
if (item.type === 'folder') {
    const hideBtn = document.createElement('button');   // 块作用域
    ...
}
div.onclick = (e) => {
    if (e.target === cb || e.target === hideBtn || hideBtn.contains(e.target)) return;  // 抛错
    setFocus(side, item);
};
```

**修法**：不要再用变量引用去做"点击豁免"，改用 DOM 语义判断。这是唯一正确写法：

```js
div.addEventListener('click', (e) => {
    // 交互控件不触发焦点切换
    if (e.target.closest('input, button, .row-action')) return;
    setFocus(side, item.id);
});
```

同时把事件绑定从 `onclick=` 全部改为 `addEventListener`，并配合"行虚拟化/整体重渲染"策略（见 §11.2）避免闭包捕获旧对象。

### 3.2 【致命】右键菜单一闪就消失

**现象**：右键文件，行背景变焦点色，但菜单看不到（或闪一下）。

**根因**：两个监听器打架。`frontend/index.html:759-763` 在行上 `showContextMenu()` 打开菜单；事件继续冒泡到 `document`，`frontend/index.html:921-931` 的 document 级 `click` / `contextmenu` 监听发现 `!elContextMenu.contains(e.target)`（因为 `e.target` 是列表行）→ 立刻 `hideContextMenu()`。

**修法**（二选一，推荐 B）：

- A：行 handler 里 `e.stopPropagation()`。缺点是任何新增监听都可能再次踩坑。
- B：**全局统一分发**。列表容器只挂一个 `contextmenu` 监听（事件委托），`document` 上的关闭逻辑改为"捕获阶段 + 命中判断"：

```js
// 唯一的打开入口（事件委托，性能更好，也天然支持列表重渲染）
elList.addEventListener('contextmenu', (e) => {
    const row = e.target.closest('.row');
    if (!row) { hideContextMenu(); return; }   // 空白处右键 → 目录级菜单
    e.preventDefault();
    const id = row.dataset.id;
    setFocusByID(side, id, { keepSelection: true });
    openContextMenu(e.clientX, e.clientY, buildMenuModel(side, id));
});

// 关闭：只在"按下的目标既不是菜单、也不是列表行"时关闭
document.addEventListener('pointerdown', (e) => {
    if (e.target.closest('.context-menu')) return;   // 点菜单内部不关
    if (e.target.closest('.row')) return;            // 点行交给行逻辑
    hideContextMenu();
}, true);
window.addEventListener('blur', hideContextMenu);
window.addEventListener('resize', hideContextMenu);
elList.addEventListener('scroll', hideContextMenu, true);
```

再加一条：菜单打开后必须 `e.preventDefault()`（禁用 WebView 原生菜单），且菜单容器 `position: fixed; z-index: 1000`。

### 3.3 【致命】隐藏的文件夹无法恢复

**现象**：恢复时报 `未找到隐藏记录: E:/KKV114/UserData/chara/female/22.7.15`。

**根因**：两边对"路径"的约定不一致。

- `app.go:861-879` 构建隐藏树时：`ID = abs`（绝对路径）、`Name = rel`（相对路径）。
- `frontend/index.html:1062` 恢复时把 **`ID`（绝对路径）** 传回后端。
- `invisible.go:396-433` 的 `RestoreFolders` 直接把入参当**相对路径**去 `kksState.KKSFolders` 里 `containsString` → 永远匹配不上 → `未找到隐藏记录`。

**修法（双保险，两个都做）**：

1. `TreeNode` 增加字段 `rel string`（相对其所属根的 POSIX 路径）。前端恢复时传 `rel`，不传 `id`。
2. 后端 `RestoreFolders` 入口做**归一化**：无论传绝对路径还是相对路径，先 `classify()` 转成相对路径再匹配。这样即使前端传错也不会坏。

```go
func (s *InvisibleStore) normalizePath(p string) (rel, side string, ok bool) {
    abs := p
    if !filepath.IsAbs(abs) {
        // 相对路径：两侧都要试
        for _, root := range []string{s.origK, s.origD} {
            cand := filepath.Join(root, filepath.FromSlash(p))
            if _, err := os.Stat(cand); err == nil {
                return s.classify(cand)
            }
        }
        // 文件已不存在时，按字符串归属判断
        if _, side, ok := s.classify(filepath.Join(s.origK, filepath.FromSlash(p))); ok {
            return filepath.ToSlash(p), side, true
        }
        return filepath.ToSlash(p), "", false
    }
    return s.classify(abs)
}
```

> 教训（写进代码注释）：**同一个概念在一处用绝对路径、另一处用相对路径，是这类 bug 的唯一来源。全项目统一：对外 ID 用绝对路径，对索引 key 用"侧 + 相对路径"。**

### 3.4 【严重】`female/` 这类管理类型根目录下，复选框变灰不可用

**根因**：`frontend/index.html:610-625` 的 `updateSelectAllState` 只统计 `n.type !== 'folder'` 的条目：

```js
const items = nodes.filter(n => n.path === path && n.type !== 'folder');
if (items.length === 0) { elSelectAll.checked = false; elSelectAll.disabled = true; return; }
```

`female/` 根目录下往往全是文件夹、没有卡片 → 全选被禁用。同理，`invisible` 模式下所有条目都是 `hidden` 类型，也会被误判。

**修法**：全选语义 = "当前目录下的**所有可见条目**（文件夹 + 文件）都勾选"。三态 `indeterminate` 必须支持。

```js
function syncSelectAll(side) {
    const rows = visibleRows(side);              // 当前目录全部条目，含文件夹
    const total = rows.length;
    const picked = rows.filter(r => isSelected(side, r.id)).length;
    const box = selectAllBox(side);
    box.disabled = total === 0;
    box.checked = total > 0 && picked === total;
    box.indeterminate = picked > 0 && picked < total;
}
```

另外，`invisible` 模式下条目**必须可勾选**（否则无法多选恢复），只是"隔离/启用"按钮变灰。

### 3.5 【界面】隐藏文件夹图标与普通文件夹不一致

**根因**：`frontend/index.html:717-720`：

```js
const icon = item.type === 'folder' ? '📁'
           : item.type === 'mod' ? '📦'
           : item.type === 'hidden' ? '🙈'      // ← 删掉这条
           : '🖼️';
```

**修法**：`hidden` 与 `folder` 使用**完全相同**的图标与字色。区分方式改为"右侧灰色小标签：已隐藏"，不靠图标。

### 3.6 【严重】依赖图越用越脏（`GlobalDepMap` 重复累积）

**根因**：`clipboard.go:301-327` 的 `afterResourceMoved`：

```go
m.GlobalDepMap[g] = append(m.GlobalDepMap[g], dst)   // 无去重
```

同一文件被移动 N 次，就会在同一 GUID 下积累 N 条相同引用。后果：`zipmodStillReferenced` 统计虚高 → 该隔离的 zipmod 隔离不掉；日志里"仍被 37 个资源引用"实际只有 3 个。

**修法**：不要"增量修补双向图"。改成 §5.4 的**派生式**设计 —— 反向图永远由正向数据 `Cards[path].GUIDs` 现算（O(n) 内存操作，几万条目毫秒级），彻底消除这类不一致。

### 3.7 【严重】跨盘移动失败会留下双份文件，且不回滚

**根因**：`manager.go:939` `moveFile` 在 `os.Rename` 失败后降级为"复制 → 校验 → 删源"。若"删源"失败，或中途进程被杀：目标已有完整副本、源仍在 → 用户看到两份，且没有任何记录说明发生了什么。

**修法**：纳入 §6 事务。`moveFile` 只负责"做一步、返回结果"，由 Tx 记录每一步的 `intent / done`，失败时逆序回滚。跨盘复制前必须检查目标盘剩余空间 ≥ 源大小 × 1.1。

### 4.2 并发模型与锁顺序（这是同类项目最容易翻车的地方）

- **一把写锁 `opMu sync.Mutex`**：所有改变磁盘状态的操作（隔离/启用/粘贴/删除/新建/重命名/隐藏）必须串行。UI 侧在操作期间禁用按钮，并在后端再加一道"正在执行，请稍候"的快速失败。
- **一把读写锁 `stateMu sync.RWMutex`**：保护 `IndexData` 与派生索引。读多写少。
- **固定锁顺序：`opMu` → `stateMu`**。全项目只允许这个方向，任何"持有 stateMu 再取 opMu"的代码都是死锁隐患。
- **扫描协程**：`ScanAll` 在独立 goroutine 中执行，自己持写锁；UI 通过 `ctx` 取消；同一时刻只允许一个扫描（`scanning atomic.Bool`）。
- **禁止在持锁期间调用 Wails 事件发射**（`runtime.EventsEmit`）。收集完事件再在锁外发。
- 所有 map 的读写必须在锁内。`-race` 测试必须过。

### 4.3 状态机（UI 与后端共用）

```
Idle ──SelectRoot──▶ Scanning ──ok──▶ Ready ──op──▶ Busy ──ok──▶ Ready
                        │                 ▲          │

```
`Busy` 期间：所有写按钮 disabled；列表可浏览；进度遮罩显示"正在移动 3/12"。

## 5. 索引与增量扫描（本次最重要的性能改造）

### 5.1 目标：把"每次启动读几万个 42MB PNG"降为"一次元数据遍历 + 只解析变化文件"

给出可量化的验收口径（假设 8000 卡片 + 3000 zipmod + 120 DLL）：

| 场景 | 现状 | 目标 |
|---|---|---|
| 冷启动（首次索引） | 3–15 分钟 | ≤ 3 分钟（8 线程并行，磁盘受限） |
| 二次启动（无变更） | 3–15 分钟（全量重扫） | **≤ 2 秒**（0 次 PNG 内容读取） |
| 单文件变更后启动 | 全量 | ≤ 2 秒 + 解析 1 个文件 |
| 切换列表目录 | 全树遍历 + 每文件夹递归统计 | ≤ 50ms（内存快照） |
| 切换焦点取预览 | 重新解码大 PNG | 首次 ≤ 200ms，之后 ≤ 5ms（缓存命中） |
| 隔离前依赖判定 | 遍历 + `os.Stat` | ≤ 1ms（纯 map） |

### 5.2 `index.json` 结构

位置：`DELCARDS/_state/index.json`（**不在 KKS_ROOT 内**，见 R2）。

```go
const indexSchemaVersion = 1

type Fingerprint struct {
    Size    int64 `json:"size"`
    ModTime int64 `json:"mtime"` // UnixNano
}

type ZipmodEntry struct {
    Fingerprint
    GUID string   `json:"guid"`
    Deps []string `json:"deps"` // 该 zipmod 通过 manifest 声明的依赖 GUID
}

type CardEntry struct {
    Fingerprint
    Kind  string   `json:"kind"`  // female_card / scene / ...
    Rel   string   `json:"rel"`   // 相对该类型资源根的路径（POSIX）
    GUIDs []string `json:"guids"` // 解析失败时为空切片（不是 nil，便于区分"未解析"）
    ParseErr string `json:"parseErr,omitempty"`
}

type PluginEntry struct {
    Fingerprint
    Rel   string   `json:"rel"`   // 相对 KKS_ROOT
    GUIDs []string `json:"guids"` // 命中的 zipmod GUID
}

type IndexData struct {
    SchemaVersion int    `json:"schemaVersion"`
    Root          string `json:"root"`      // 绝对路径；不一致 → 全量重建
    ScannedAt     int64  `json:"scannedAt"`

    Zipmods map[string]*ZipmodEntry `json:"zipmods"` // key: 绝对路径
    Cards   map[string]*CardEntry   `json:"cards"`   // key: 绝对路径
    Plugins map[string]*PluginEntry `json:"plugins"` // key: 绝对路径

    // 用户显式要求保留的字段
    PluginDepMap map[string][]string `json:"pluginDepMap"` // GUID -> 引用它的 DLL 相对路径
}
```

**只持久化正向数据。** `GlobalDepMap`、`GuidToZipmod`、`MissingGUIDs`、文件夹统计**全部不落盘**，启动时由正向数据 O(n) 派生（§5.4）。理由：落盘就要双写，双写就会不一致，不一致就会出现"明明还在用却提示可隔离"这种致命错误。

### 5.3 增量扫描算法

```go
type ProgressFunc func(phase string, done, total int)

// ScanAll 是全项目唯一允许"扫盘读内容"的入口。
// force=false 时走增量；force=true 时忽略指纹全部重解析（用户点"重新扫描"）。
func (m *Manager) ScanAll(ctx context.Context, force bool, progress ProgressFunc) (ScanStats, error)
```

流程（严格按此顺序）：

1. **加载旧索引**：`index.Load()`。若 `SchemaVersion` 不符、`Root` 不符、文件损坏 → 视为空索引（不报错，直接全量）。
2. **一次元数据遍历**，收集三组待对比集合。**只用 `filepath.WalkDir` + `d.Type()` + `d.Info()`，不打开任何文件**：
   - `mods/**/*.zipmod`
   - 6 类资源根下 `*.png`
   - `BepInEx/plugins/**/*.dll`、`BepInEx/core/**/*.dll`
3. **diff**：
   ```
   new     : 路径不在旧索引
   changed : size 或 mtime 不同
   removed : 旧索引有、本次遍历没有
   same    : 其余（直接复用旧条目，零 IO）
   ```
4. **并行解析** `new + changed`：
   - worker 数 = `min(8, runtime.NumCPU())`（磁盘密集，超过 8 无收益且伤机械盘）。
   - 每个 worker 独立，结果写 channel，主协程汇总（不要并发写同一个 map）。
   - 单文件失败**不中断**：写入 `CardEntry{ParseErr: ...}`，计入 `FailedFiles`。
   - 进度回调按 `(done, total)` 节流到 **≥100ms 一次**，否则前端事件会被打爆。
5. **清理** `removed`（从三个 map 删除）。
6. **派生反向索引**（§5.4）。
7. **原子保存** `index.json`：写 `index.json.tmp` → `Sync()` → `Rename`。保存失败只记警告，不影响本次使用。
8. **更新内存状态**：`stateMu.Lock()` 内整体替换索引指针（不要逐字段改）。

**关键细节（必须实现，否则"增量"是假的）**：

- mtime 用 `UnixNano`，不要用格式化字符串。
- Windows 上 FAT/exFAT 的 mtime 精度是 2 秒，所以**判定 changed 的条件是 `size 不同 || mtime 不同`**，两者全同才算 same。可接受极小概率漏检（用户可点"重新扫描"强制）。
- 解析 PNG 时**只读 IEND 之后的追加数据**（卡片依赖全在尾部）。给出实现要点：
  ```go
  // locateAppendedTail 顺序走 PNG chunk 头（8 字节），跳过 IDAT 负载，找到 IEND 后返回其结束偏移。
  // 只 seek 不读负载，42MB 的卡只需几十次 8 字节读。
  func locateAppendedTail(f *os.File, size int64) (int64, error)
  ```
  若 `size - tailOffset > 64MB`（异常卡），放弃尾部优化，退回整文件读取并记 warn。
- 若尾部解析失败，退回现有的整文件双通道解析（保证兼容性），但**只在 changed 时发生**。

### 5.4 派生索引（唯一真源原则）

```go
// derive 由正向数据重建全部反向索引，纯内存，O(n)。
// 只在两处调用：扫描结束、事务提交后。
func (s *IndexState) derive() {
    s.GuidToZipmod = make(map[string]string, len(s.Index.Zipmods))
    for path, z := range s.Index.Zipmods {
        if z.GUID == "" { continue }
        if _, dup := s.GuidToZipmod[z.GUID]; !dup {
            s.GuidToZipmod[z.GUID] = path // 同 GUID 多文件：保留字典序最小，稳定可预期
        }
    }
    s.GlobalDepMap = make(map[string][]string, len(s.GuidToZipmod))
    for path, c := range s.Index.Cards {
        for _, g := range c.GUIDs {
            s.GlobalDepMap[g] = append(s.GlobalDepMap[g], path)
        }
    }
    // 每个列表排序，保证日志与 UI 顺序稳定（便于测试断言）
    for g := range s.GlobalDepMap { sort.Strings(s.GlobalDepMap[g]) }
    s.MissingGUIDs = ... // 被引用但 GuidToZipmod 中不存在
}
```

**禁止**再写任何 `m.GlobalDepMap[g] = append(...)` 形式的增量修改。文件移动后只改 `Index.Cards`（删旧 key、加新 key），然后 `derive()`。几万条目 derive 约 5–20ms，完全可以每次操作后跑一遍。

### 5.5 目录快照缓存（列表秒开）

`ListDir` 不允许每次都 `os.ReadDir` 全树。做一层按目录的缓存：

```go
type DirSnapshot struct {
    ModTime int64            // 目录自身 mtime，用于失效
    Entries []DirEntryDTO    // 只含该目录直接子项
}
// cache: map[string]*DirSnapshot  （key = 绝对路径）
```

失效策略：读取前 `os.Stat(dir)` 比对 `ModTime`；不等则重建该目录快照（只读一级，不递归）。任何事务提交后，清空受影响目录及其所有祖先的快照（按路径前缀批量删）。

### 5.6 文件夹统计：一次自底向上聚合，而不是每个文件夹递归

现状 `app.go:493-565` 的 `buildTreeLocked` 对**每个**文件夹调用 `computeFolderStats`（内部 `dirSize` 递归）→ 8000 文件 / 500 目录的树，等于遍历 500 次全树，O(n²)。

**修法**：

```go
// 一次后序遍历，得到每个目录的 {直接子文件夹数, 直接卡片数, 递归文件数, 递归字节数}
func aggregateStats(dir string, out map[string]*Stats) *Stats
```
- 只对"当前展示的目录"及其直接子目录计算，**不要**为整棵树计算。
- 结果进 `DirSnapshot.Stats`，与快照同生命周期。
- 深浅统计分开：`directCards`（右栏下窗格需要）与 `recursiveFiles`（"共 N 个文件"需要），不要混用。

### 5.7 缩略图两级缓存

现状 `preview.go` 每次切焦点都重新解码（最坏 42MB PNG → 解码 → 缩放 → JPEG）。做两级缓存：

1. **内存 LRU**：`map[path]entry` + 双向链表，容量 128 张，key = `path + "|" + fingerprint`。
2. **磁盘缓存**：`DELCARDS/_state/thumb/<sha1(path+fingerprint)[:2]>/<sha1>.jpg`，JPEG q82，320×400 上限。文件大小约 20–60KB。
3. 命中顺序：内存 → 磁盘 → 解码。
4. 磁盘缓存总量超过 512MB 时，按 LRU 清理（后台，低优先级，不阻塞 UI）。
5. 预览请求必须支持**取消**：前端切焦点时 `previewSeq` 已做丢弃，后端再加"若该请求的 seq 已被更新请求取代则不写缓存"（避免无用的解码占用）。

### 5.8 DLL 扫描的缓存

`PluginEntry` 带指纹。DLL 未变 → 直接复用上次的 `GUIDs`，不读文件内容。DLL 变了，或 zipmod 集合变了（新增 GUID 需要重新匹配），才重扫。判定"zipmod 集合变了"用 `sha1(sorted(guids))` 存在 `IndexData.GuidSetHash`。**这一条能避免"每次操作都重扫 DLL"**。

## 6. 事务引擎（解决"文件被弄得稀巴烂"）

### 6.1 三段式：预检 → 计划 → 执行（可回滚）

```go
type StepKind string
const (
    StepMove    StepKind = "move"
    StepCopy    StepKind = "copy"
    StepMkdir   StepKind = "mkdir"
    StepRename  StepKind = "rename"
    StepTrash   StepKind = "trash"   // 删除 = 移入 _trash
)

type Step struct {
    Kind StepKind
    Src  string
    Dst  string
    // 执行时填充
    State string // intent / done / rollback-done
}

type Tx struct {
    ID        string      // 20261113-164800-a3f2
    Op        string      // isolate / paste / delete / mkdir / rename / hide
    Dir       string      // DELCARDS/_journal/<ID>/
    Steps     []Step
    createdAt int64
}

func (t *Tx) Run() error   // 逐步执行，每步前写 journal(intent)，成功后写 done
func (t *Tx) Rollback() error // 逆序回滚
```

**语义硬约束**：

1. **预检必须在任何写操作之前完成**。预检失败 → `return` 时磁盘零变化，并返回结构化冲突列表。
2. 每个 Step 执行前，先把 `intent` 追加写入 `journal.json` 并 `Sync`。这样"执行到一半断电"也能恢复。
3. 任一步失败 → 立即停止 → `Rollback()` → 返回 `{success:false, rolledBack:true, failedStep, logs}`。
4. 回滚规则：

| 步骤 | 回滚动作 |
|---|---|
| `move` (done) | `moveFile(dst, src)`；若 src 已存在（极端），移到 `src.conflict-<txid>` 并 error 记录 |
| `move` (intent 但未 done) | `dst` 存在且 `src` 不存在 → 移回；`dst` 是半成品 → 删 `dst` |
| `copy` (done 或半成品) | 删除本次创建的副本（只删 `dst` 及本 tx 记录创建的子路径） |
| `mkdir` | `os.Remove`（仅当空；非空则保留并 warn） |
| `trash` | 从 `_trash/<txid>/...` 移回原路径 |
| `rename` | 改回原名 |

5. **崩溃恢复**：启动时扫描 `DELCARDS/_journal/*/journal.json`，凡 `state != "committed"` 的 Tx：
   - 默认**自动回滚**（这是用户要的"中途失败直接还原"）。
   - 回滚结果写入启动日志，UI 用一条 warn 提示："检测到上次未完成操作（粘贴 12 项），已自动还原。"
   - 回滚失败 → 弹窗阻断，并提示"请打开 DELCARDS/_journal/<txid>/ 查看详情"。

### 6.2 备份策略（不要无脑全量复制）

用户要求"操作前先备份"。**但把 40GB 卡组复制一遍是不可接受的**。正确做法是按操作性质区分：

| 操作 | 可逆性 | 保障手段 | 额外备份 |
|---|---|---|---|
| 隔离 / 启用（移动） | 完全可逆 | journal 逆序移回 | 不需要（移动本身可逆，复制反而是浪费） |
| 粘贴-剪切 | 完全可逆 | journal | 跨盘时先检查空间；不预复制 |
| 粘贴-复制 | 可逆 | journal（删除新建副本） | 不需要 |
| 删除 | **不可逆** | 移入 `_trash/<txid>/` 保留原相对结构 | `_trash` 就是备份 |
| 覆盖 | 禁止 | — | — |
| 隐藏空文件夹 | 可逆 | 目录树 JSON + journal | JSON 即备份 |

`DELCARDS/_backup/<txid>/` 保留给"用户手动勾选『操作前完整备份』"的场景（设置项，默认关闭），实现为执行前 `copyPath` 到备份区，日志注明备份路径。**默认路径下不产生额外拷贝**，这是对性能与安全的正确权衡。

### 6.3 预检清单（全部实现，缺一不可）

```go
type Preflight struct {
    Conflicts   []Conflict   // 目标同名
    Blocked     []Block      // 依赖保护 / DLL 保护 / 只读 / 占用
    Invalid     []Invalid    // 非法名 / 路径超长 / 目标在源内部
    SpaceNeeded int64
}
```

逐项检查：

1. **同名冲突**：`os.Lstat(dst)` 存在 → 记录冲突。**一次性收集全部冲突**（现状 `clipboard.go:177-180` 一遇冲突就 `break`，只报第一个，用户修一个再撞一个，体验极差）。
2. **目标在源内部**：`copyPath("A", "A/B")` 会无限递归。必须判定 `Dst` 是否为 `Src` 的子孙（`filepath.Rel` + 前缀判断），命中即拒绝。
3. **源码目标**：`Src == Dst` → 直接拒绝（现状 PNG 允许同路径，会产生"复制到自身"的怪行为）。
4. **路径长度**：Windows MAX_PATH 260。`len(dst) > 255` → 拒绝并给出具体路径。
5. **非法字符**：`< > : " | ? *` 及结尾空格/点。新建/重命名时必须校验。
6. **只读属性**：`info.Mode()&0200 == 0` → 拒绝。
7. **文件占用**：Windows 上尝试以 `O_RDWR` 打开（不读内容）失败 → 判定被占用，拒绝该条。
8. **磁盘空间**：跨盘复制时 `GetDiskFreeSpaceEx` 检查 `>= 源大小 * 1.1`。
9. **依赖保护**（隔离类）：§8 三道防线。

### 6.4 两阶段 API（用户要的"提前报错"）

所有破坏性操作拆成两次调用：

```
Plan(paste|delete|isolate)  →  { planId, summary, conflicts[], blocked[], steps[] }   // 零副作用
Commit(planId, options)     →  { txId, moved, skipped, failed, logs[] }               // 执行
```

UI 行为：
- `Plan` 返回 `conflicts` 非空 → **弹窗**列出前 10 条（"还有 N 条"），按钮：`取消` / `全部跳过冲突项` / `自动重命名（追加 (1)）`。
- `blocked` 非空（依赖保护）→ 弹窗展示原因，只能"取消"或"仅执行未阻断项"。
- 全部通过 → 直接 `Commit`（移动类操作不再二次确认，避免烦人；删除类必须二次确认）。
- `planId` 有效期 5 分钟，过期/已被消费则返回 `plan expired`。

## 8. 插件硬编码依赖检查（新功能，必须实现）

### 8.1 为什么需要

有些 BepInEx 插件（.dll）在代码里硬编码了 zipmod 的 GUID 字符串。把该 zipmod 移走，游戏不报"缺 mod"，而是插件直接抛异常/崩溃 —— 比缺卡更难排查。所以必须有第二道防线。

### 8.2 扫描范围与匹配

- 目录：`KKS_ROOT/BepInEx/plugins`、`KKS_ROOT/BepInEx/core`，递归全部子目录。
- 目标：`*.dll`（大小写不敏感）。
- 匹配：**二进制字节流包含匹配**（`bytes.Contains`），大小写敏感。
- 同时匹配 **UTF-8** 与 **UTF-16LE** 两种编码形态（部分插件资源以 UTF-16 存储）。
- 过滤条件：`len(guid) >= 8` 才参与匹配（KKS GUID 普遍较长，短串会产生大量误判）。

### 8.3 函数签名（用户明确要求，签名不许改）

```go
// ScanPluginsForDependencies 扫描 BepInEx 下的 DLL，构建 GUID -> []DLL 的硬编码依赖图。
```

### 8.4 实现骨架

```go
func (m *Manager) ScanPluginsForDependencies() error {
    m.stateMu.Lock()
    idx := m.idx.Index
    guids := make([]string, 0, len(idx.Zipmods))
    for _, z := range idx.Zipmods {
        if len(z.GUID) >= 8 { guids = append(guids, z.GUID) }
    }
    m.stateMu.Unlock()
    sort.Strings(guids)

    setHash := hashStrings(guids)
    dlls, err := collectDLLs(m.KksRoot) // BepInEx/plugins + BepInEx/core
    if err != nil { return err }

    type result struct{ path string; hits []string }
    out := make(chan result, len(dlls))
    sem := make(chan struct{}, 4) // DLL 通常巨大，4 并发足够，避免打满内存带宽
    var wg sync.WaitGroup

    for _, p := range dlls {
        wg.Add(1)
        go func(path string) {
            defer wg.Done()
            sem <- struct{}{}; defer func(){ <-sem }()

            // 1) 指纹未变且 GUID 集未变 → 复用
            if old, ok := m.pluginCache[path]; ok && old.fp.equal(statOf(path)) && old.setHash == setHash {
                out <- result{path, old.guids}; return
            }
            // 2) 读取并匹配
            info, err := os.Stat(path)
            if err != nil || info.Size() > 128<<20 { // >128MB 跳过并记 warn
                out <- result{path, nil}; return
            }
            data, err := os.ReadFile(path)
            if err != nil { out <- result{path, nil}; return }

            hits := matchGUIDs(data, guids)   // 见 8.5
            out <- result{path, hits}
        }(p)
    }
    go func(){ wg.Wait(); close(out) }()

    pluginDep := make(map[string][]string, 256)
    plugins  := make(map[string]*PluginEntry, len(dlls))
    for r := range out {
        rel, _ := filepath.Rel(m.KksRoot, r.path)
        plugins[r.path] = &PluginEntry{Fingerprint: statOf(r.path), Rel: filepath.ToSlash(rel), GUIDs: r.hits}
        for _, g := range r.hits {
            pluginDep[g] = append(pluginDep[g], filepath.ToSlash(rel))
        }
    }
    for g := range pluginDep { sort.Strings(pluginDep[g]) }

    m.stateMu.Lock()
    m.idx.Index.Plugins = plugins
    m.idx.Index.PluginDepMap = pluginDep
    m.pluginCache = ...        // 同步更新缓存
    m.stateMu.Unlock()
    return m.saveIndex()       // 原子写
}
```

### 8.5 匹配实现（性能必须交代清楚）

GUID 数量 ~3000，DLL 总量可达数百 MB。**朴素做法 = 3000 × 每个 DLL 全扫一遍**，冷启动会到几十秒级别。给出两级策略：

1. **默认实现**：`bytes.Contains` 逐 GUID。因为 `bytes.Contains` 内部走汇编优化的 `IndexByte`，实测吞吐 ~10GB/s 量级，3000 × 200MB = 600GB ≈ 40–60 秒，**仅冷启动一次**，且按指纹缓存后不再发生。可接受，代码 20 行。
2. **优化闸门**：若实测冷启动 > 20 秒，切 Aho–Corasick（单趟扫描，O(totalBytes + matches)）。要求自行实现（不引入外部依赖），放 `internal/plugin/ac.go`，节点 children 用 `map[byte]int32` 避免 `[256]int32` 的内存爆炸。**不要过度设计**：先做方案 1，用日志打印实际耗时，超阈值再上方案 2。

```go
// matchGUIDs 返回 data 中出现的 GUID 列表（UTF-8 与 UTF-16LE 两种形态）。
func matchGUIDs(data []byte, guids []string) []string {
    hits := make([]string, 0, 8)
    for _, g := range guids {
        if bytes.Contains(data, []byte(g)) || bytes.Contains(data, utf16le(g)) {
            hits = append(hits, g)
        }
    }
    return hits
}
```

### 8.6 三道防线（隔离判定的唯一入口）

```go
func (m *Manager) IsZipmodSafeToMoveEx(guid string, moving map[string]bool) (bool, string) {
    if strings.TrimSpace(guid) == "" {
        return false, "无法识别 GUID，无法确认依赖关系，已保留原文件。"
    }
    m.stateMu.RLock()
    defer m.stateMu.RUnlock()

    // 第一道：卡片/场景依赖（排除本次正在移动的文件）
    var refs []string
    for _, p := range m.GlobalDepMap[guid] {
        if moving[p] { continue }
        if _, err := os.Stat(p); err != nil { continue } // 只统计真实存在的
        refs = append(refs, p)
    }
    if len(refs) > 0 {
        return false, fmt.Sprintf("GUID %q 仍被 %d 个资源文件引用，例如：%s", guid, len(refs), firstN(refs, 3))
    }
    // 第二道：插件硬编码依赖
    if dlls := m.PluginDepMap[guid]; len(dlls) > 0 {
        return false, fmt.Sprintf("[插件保护] GUID %q 被插件 %q 硬编码引用，跳过隔离以防崩溃。", guid, strings.Join(dlls, ", "))
    }
    // 第三道：其它 zipmod 依赖它（ModDeps 反查）
    if deps := m.modDependents(guid); len(deps) > 0 {
        return false, fmt.Sprintf("GUID %q 被其它 zipmod 依赖：%s", guid, firstN(deps, 3))
    }
    return true, ""
}
```

**强制要求**：所有会移动 zipmod 的代码路径（`Isolate`、`Paste`、一键隔离多余 zipmod、未来的拖拽）**必须**只调用这一个函数做判定。禁止在别处再写一份"检查逻辑"。日志文案严格使用上面两句（含 `[插件保护]` 前缀），便于用户搜索与测试断言。

### 8.7 每次操作后的依赖校验

用户要求"每一步都检查 zipmod 是否存在"。**实现方式是查索引，不是扫盘**：

```go
// verifyAfterTx 在事务提交后执行，只查内存索引。
func (m *Manager) verifyAfterTx(affectedCards []string) VerifyReport {
    // 1. 受影响卡片的 GUID 是否都能在 GuidToZipmod 找到
    // 2. 找不到的 → MissingGUIDs；若该 GUID 在 DEL-zipmod 中存在 → 标记 "可从隔离区恢复"
    // 3. 返回 {missing:[{guid, cards[], removableFromTrash:bool}], extraMods:[...]}
}
```

UI 展示在状态栏红点 + 日志 warn，并提供"一键恢复缺失 zipmod"（把 `DEL-zipmod` 中对应 GUID 的文件移回 `mods/`，本身也是一个事务）。

## 9. 操作规则明细（逐条照做）

### 9.1 隔离（左 → 右）

1. 展开选中项：文件夹递归展开为文件列表（`collectFilesStrict`，遇错即整批失败——移动场景不允许容忍）。
2. 汇总被选文件的全部 GUID → `moving` 集合（含文件路径）。
3. 对每个 GUID：`IsZipmodSafeToMoveEx(guid, movingSet)`。
   - 不允许 → 记 `[保留 MOD]` 日志，**不阻断卡片隔离**（卡片照移，mod 保留）。
   - 允许 → 加入移动计划。
4. 保留相对目录结构：`DEL-<kind>/<relDir>/<file>`。
5. 目标目录不存在 → `MkdirAll`（并在 journal 记 `mkdir`）。
6. 目标已存在同名 → **冲突，整批取消**（走 §6.4 弹窗），不跳过、不覆盖。
7. 提交 Tx → 更新 `Cards`（删源 key、加目标 key）→ `derive()` → `verifyAfterTx()` → 保存索引。

### 9.2 启用（右 → 左）

对称。目标父目录不存在时：先查隐藏索引 `EnsurePathForOperation` 重建被隐藏的祖先目录，再落文件。冲突同样整批取消。

### 9.3 粘贴

- 源集合来自剪贴板（`op` / `paths` / `sourceSide`）。
- **zipmod 特殊语义**：无论复制还是剪切，一律执行"移动"（复制到隔离区等于没隔离，这是已确定的正确决策）。
- PNG：允许同侧任意路径，但 `Src == Dst` 拒绝、`Dst` 在 `Src` 内拒绝。
- 剪切完成后清空剪贴板；复制不清空。
- 剪贴板必须**跨重启持久化**（写到 `DELCARDS/_state/clipboard.json`），路径失效时在 UI 上标灰。

### 9.4 删除（仅自由模式）

- 二次确认弹窗，明确写"将移入回收站，可从「回收站」还原"。
- 实现为 `trash`：`DELCARDS/_trash/<txid>/<side>/<relPath>`，保留结构。
- 「回收站」作为新的管理类型出现在下拉框，支持浏览 / 还原 / 永久删除（永久删除要输入文件夹名确认）。
- 删除非空文件夹 → 整棵子树移入 trash（不是逐个文件），trash 里必须能完整还原。

### 9.5 新建文件夹 / 重命名

- 新建：目标目录 + 名称校验（非法字符、重名、长度）→ `Mkdir` → journal。
- 重命名：同目录内改名，目标存在则拒绝；扩展名变更警告（`.png` → 其它会丢依赖解析）。
- 两者都刷新 `DirSnapshot` 与索引 key。

### 9.6 隐藏空文件夹

1. 只有**递归文件数为 0** 的文件夹才渲染隐藏按钮（数据来自索引/快照，不额外扫盘）。
2. 点击非空文件夹（数据过期）→ **必须弹窗**：`无法删除，不是空文件，存在 N 个文件`。不仅要写日志。
3. 隐藏成功 → 记录目录树 → 删除源空文件夹 → 刷新列表 → toast 提示"已隐藏，可在「隐藏的文件夹」中恢复"。

### 9.7 恢复隐藏文件夹

- 入参归一化（§3.3）。
- 重建目录树 → 从隐藏列表移除 → 原子写 JSON。
- 目标已存在 → 合并且不删除已有内容，日志说明。
- 单选/多选/全选都要能用（§3.4）。

### 11.2 渲染策略

- 一次渲染 = `state → 生成 DOM 片段 → 一次性 replaceChildren`。不要增量 patch 单行（状态与 DOM 会漂移）。
- 列表超过 300 行时启用窗口化（只渲染可视区 ±10 行）。低于 300 行不做，避免过度设计。
- 渲染函数必须**纯**：只读 state，不发请求。请求在事件里发，回来只更新 state 再触发渲染。
- 每个异步请求带 `seq`（当前已有 `previewSeq`），回来时 `seq !== currentSeq` 直接丢弃。

```
在资源管理器中显示
```

菜单实现要求：
- 最大高度 `min(70vh, 内容高)`，超出滚动。
- 打开时先 `visibility:hidden; display:block` 量尺寸，再定位（避免闪烁）。
- 靠近边缘自动翻转方向。
- 菜单项点击后立即关闭，再执行（避免长操作时菜单悬空）。

### 11.6 对话框体系（必须有，不能再"只写日志"）

| 类型 | 用途 | 交互 |
|---|---|---|
| Toast | 成功/轻提示 | 右下角，2.5s 自动消失，最多堆 3 条 |
| Confirm | 删除/危险操作 | 居中，主按钮左（危险色），次按钮右 |
| Alert | 阻断性错误（无法粘贴、无法隐藏） | 居中，单按钮"知道了"，必须能被用户看到 |
| Conflict | 冲突清单 | 列表 + 三个处置选项（取消/跳过/重命名） |
| Progress | 长操作 | 底部条 + 取消按钮（仅扫描可取消） |
| LogModal | 日志 | §10.3 |

**硬要求**：后端返回 `success:false` 且属于"用户操作失败"（不是"列表为空"这类提示）时，前端**必须**弹 Alert 或 Conflict，不允许只 `log()`。这是用户抱怨"粘贴出错不会弹窗提示"的直接修复。

### 11.7 与后端的错误约定

后端所有绑定方法返回统一结构：

```json
{ "success": true, "code": "OK", "message": "已隔离 12 项", "data": {...}, "logs": [...] }
```

`code` 用于前端分支，`message` 直接展示给用户（**必须是人话，中文，含具体文件名**）。

| code | 含义 | 前端行为 |
|---|---|---|
| `OK` | 成功 | Toast |
| `PLAN_CONFLICT` | 有同名冲突 | Conflict 弹窗 |
| `PLAN_BLOCKED` | 依赖保护 | Alert + 列出被保护项 |
| `PLAN_EXPIRED` | 计划过期 | Alert + 重新 Plan |
| `BUSY` | 有操作在执行 | Toast warn，忽略本次点击 |
| `NO_ROOT` | 未选根目录 | Alert + 高亮选择按钮 |
| `IO_ERROR` | 磁盘错误 | Alert（含路径与系统错误码）+ 提示查看日志 |
| `ROLLED_BACK` | 执行失败已回滚 | Alert（"操作已取消，文件已还原"）+ 打开日志 |

## 13. 日志与提示规范

### 13.1 日志分级与文案格式

```go
type LogEntry struct {
    Seq   int64  `json:"seq"`
    TS    int64  `json:"ts"`
    Level string `json:"level"` // info / success / warn / error
    Scope string `json:"scope"` // scan / isolate / paste / plugin / index / ui
    Msg   string `json:"msg"`
}
```

统一格式：`[<scope>] <动作> <对象> → <结果>`

必须存在的日志（测试会断言）：

- `[plugin] GUID "abc" 被插件 "Foo.dll" 硬编码引用，跳过隔离以防崩溃。`（前缀与句式固定，见 §8.6）
- `[isolate] 保留 zipmod "X.zipmod"：仍被 3 个资源引用。`
- `[paste] 预检失败：目标已存在 "a.png"（共 4 项冲突），未做任何改动。`
- `[tx] 回滚完成：撤销 7 步，文件已恢复原状。`
- `[index] 增量扫描：复用 7931，解析 12，移除 3，耗时 1.4s。` ← **这一条是"没有重复扫盘"的证据**

### 13.2 提示文案要求

- 全部中文，口语化，**带具体对象**。
- 不说"操作失败"，要说"无法粘贴：目标已存在同名文件 `子1.png`"。
- 破坏性操作明确说明后果与补救路径："已移入回收站，可在「回收站」还原。"
- 禁止把 Go 的 `err.Error()` 原文直接丢给用户（含 `syscall` 错误号），必须包装：`读取失败（文件被占用或权限不足）：C:\...`。

## 16. 反模式黑名单（看到就该改）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 渲染时遍历整个目录树算统计 | O(n²) IO，界面卡死 | 快照 + 一次聚合（§5.5/5.6） |
| 每次启动全量解析所有 PNG | 用户等 10 分钟 | 指纹增量（§5.3） |
| 用绝对路径当索引 key，又用相对路径查 | 必然"找不到记录" | 索引 key = 侧 + 相对路径；对外 ID = 绝对路径，入口归一化（§3.3） |
| 反向依赖图增量 `append` | 重复累积，判定失真 | 单一真源 + `derive()`（§5.4） |
| 在 `if` 块里 `const x`，块外引用 | ReferenceError，功能静默失效 | 事件委托 + `closest`（§11.1） |
| `document` 上全局监听关菜单，又不禁用冒泡 | 菜单闪现即消失 | 单一开关入口 + 捕获阶段命中判断（§3.2） |
| 失败只 `console.log` / 只写日志 | 用户以为操作成功 | Alert / Conflict 弹窗 + 日志（§11.6） |
| 遇冲突 `break` 只报第一个 | 用户逐个撞墙 | 一次性收集全部冲突（§6.3） |
| 无锁并发写 map | 偶发崩溃，难复现 | `opMu` → `stateMu`，`-race` 固化（§4.2） |
| 在持锁期间发 UI 事件 | 死锁 / 事件乱序 | 收集后锁外发（§4.2） |
| 无脑全量备份 | 复制 40GB，操作变 20 分钟 | journal 可逆 + 删除进 trash（§6.2） |
| 一次性重写全部代码 | 引入大量回归，无法定位 | 阶段化演进，每阶段可编译（§15） |
| 用 emoji 当图标体系 | 跨系统渲染不一致，显廉价 | 内联 SVG + 统一 stroke（§10.4） |
| 前端自己拼日志数组 | 刷新即丢，无法导出 | 后端环形缓冲 + 增量订阅（§10.3） |
